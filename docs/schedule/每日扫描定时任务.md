### 3. 扫描维度与检查清单

#### 3.1 设计缺陷扫描（🔴 最高优先级）

- [ ] **分层架构违规**：Service 层是否直接引用 Mapper？Controller 是否包含业务逻辑？API 层是否反向依赖 Business 模块？
- [ ] **领域模型污染**：Entity 是否被直接返回给前端？VO/DTO/AO 是否混用？是否出现跨层传输的裸 Map/JSONObject？
- [ ] **接口设计缺陷**：Manager 接口与实现是否分离？Service 是否返回 VO？Convert 是否使用 MapStruct？
- [ ] **配置设计缺陷**：是否使用 `@Value` 注入（应使用 `@ConfigurationProperties`）？配置类是否缺少
  `@ConditionalOnProperty`？
- [ ] **异常体系缺陷**：是否抛出 `RuntimeException`？是否硬编码错误码？异常是否被吞掉（空 catch）？
- [ ] **自动配置缺陷**：`META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 是否完整？配置顺序是否正确？
- [ ] **循环依赖**：模块间是否存在循环依赖？Bean 间是否存在循环依赖？
- [ ] **扩展性缺陷**：是否缺少 SPI 扩展点？是否硬编码实现类？策略模式是否合理使用？
- [ ] **包结构缺陷**：包命名是否符合 `com.carlos.{service}` 规范？领域模型包是否按 param/dto/vo/ao/entity/enums/excel 分层？

#### 3.2 功能完善度扫描（🟡 高优先级）

- [ ] **核心功能缺失**：Starter 模块是否缺少关键配置属性类？是否缺少 `spring.factories` 或 `.imports` 注册？
- [ ] **健康检查缺失**：是否缺少 Spring Boot Actuator 健康检查？自定义 HealthIndicator 是否实现？
- [ ] **监控埋点缺失**：关键方法是否缺少 Micrometer 指标？异步任务是否缺少链路追踪？
- [ ] **参数校验缺失**：Controller 入参是否缺少 `@Valid`？自定义校验注解是否完善？
- [ ] **文档缺失**：公开 API 是否缺少 Swagger/Knife4j 注解？复杂业务方法是否缺少 JavaDoc？
- [ ] **测试缺失**：核心逻辑是否缺少单元测试？集成测试是否覆盖主流程？测试是否使用自动回滚？
- [ ] **降级熔断缺失**：Feign 接口是否都有 FallbackFactory？Redis 故障时是否有降级策略？
- [ ] **国际化缺失**：错误消息是否硬编码中文？是否支持 i18n？
- [ ] **多租户缺失**：多租户模块是否完整？租户隔离是否覆盖所有数据操作？
- [ ] **示例缺失**：每个 Starter 是否都有对应的 `carlos-sample-xxx` 示例模块？示例是否覆盖核心功能？

#### 3.3 代码可优化点扫描（🟢 中优先级）

- [ ] **性能优化**：N+1 查询问题、大表缺少索引提示、循环内 RPC 调用、Redis 大 Key、慢 SQL
- [ ] **并发优化**：共享可变状态、锁粒度太大、线程池参数不合理、CompletableFuture 使用不当
- [ ] **内存优化**：大对象常驻内存、缓存无限增长、流未关闭、toArray(new T[0]) 优于 toArray(new T[size])
- [ ] **算法优化**：树形结构递归深度过大、List.contains() 遍历查找（应使用 Set）、字符串拼接（应使用 StringBuilder）
- [ ] **Spring Boot 最佳实践**：`@Autowired` 字段注入（应使用构造器注入）、`@PostConstruct` 替代方案、不必要的
  `@ComponentScan`
- [ ] **日志优化**：日志参数未使用占位符、DEBUG 日志未加 `isDebugEnabled()`、异常堆栈丢失
- [ ] **代码重复**：工具类方法重复（与 Hutool/Guava 重叠）、相似逻辑未抽取、魔法值硬编码

#### 3.4 安全检查清单（🔴 最高优先级）

- [ ] 是否存在 MD5/SHA1 等弱密码编码器
- [ ] ObjectMapper Visibility 配置是否过宽（ANY → 应 PUBLIC_ONLY）
- [ ] Redis 中是否存储敏感 Token 明文
- [ ] WebClient/RestTemplate 是否配置超时和重试
- [ ] 静态工具类（RedisUtil 等）是否导致难以测试
- [ ] 匿名内部类是否影响 Native Image 编译（应使用 lambda 或独立类）
- [ ] Map/Cache 是否有内存泄漏风险（无过期清理策略）
- [ ] SQL 注入风险：`${}` 拼接、动态表名/列名未白名单校验
- [ ] 敏感配置是否硬编码（密码、密钥、AK/SK）
- [ ] 文件上传是否限制类型和大小、路径遍历风险
- [ ] 反序列化安全风险：是否校验类白名单
- [ ] **License 安全**：生产环境是否误包含 `carlos-spring-boot-starter-license-generate`
- [ ] **国密安全**：SM2/SM4 密钥是否硬编码或存储在配置文件明文

#### 3.5 依赖与技术债务扫描

- [ ] 依赖版本是否严重落后（与当前最新稳定版差距 > 2 个小版本）
- [ ] 是否存在已知 CVE 漏洞（搜索 `https://osv.dev/` 或 Maven Central Security）
- [ ] 是否存在已弃用的 API 调用（Spring Boot 3.x 迁移残留）
- [ ] `javax.*` 包是否还有残留（应全部迁移到 `jakarta.*`）
- [ ] 是否存在 SNAPSHOT 依赖用于生产环境

#### 5.2 分析执行方法

对每个组件执行以下步骤：

1. **搜索最新特性**：使用 web_search 搜索该组件最新版本的 Release Notes、新特性介绍、最佳实践
2. **代码扫描匹配**：在项目代码中搜索该组件相关的配置和用法，判断以下问题：
    - ❓ **是否使用了基础功能，而忽略了高级特性？**（如只用了 Redis String，没用 Redisson 的分布式集合/队列）
    - ❓ **是否有更好的替代写法？**（如手动分页 → MyBatis-Plus 分页插件；手动锁 → Redisson 分布式锁）
    - ❓ **是否存在性能更优的特性未启用？**（如 POI 的 SXSSF 流式写入大 Excel；Caffeine 的异步加载）
    - ❓ **是否有安全增强特性未使用？**（如 Fastjson autoType 白名单；Druid WallFilter）
    - ❓ **是否有可简化代码的特性？**（如 MapStruct 的构造函数映射；Spring Boot 的 HTTP Interface）
3. **输出利用建议**：针对每个组件，输出：
    - **当前使用方式**（从代码中扫描到的实际用法）
    - **未被利用的潜力特性**（列出 2~5 个最适合本项目的高级特性）
    - **推荐应用场景**（具体到哪个模块、哪个功能点可以使用）
    - **预期收益**（性能提升 / 代码简化 / 安全增强 / 功能增强）
    - **实施难度**（低/中/高，附带代码示例）

## 扫描规范与约束

### 代码片段规范

- 引用的代码必须**包含完整的方法签名或类定义上下文**
- 必须标注**精确的文件路径和行号范围**
- 代码片段使用 ```java 语法高亮
- 若涉及多文件关联，需分别列出

### 问题分级标准

| 级别              | 定义                   | 响应时效     | 示例                             |
|-----------------|----------------------|----------|--------------------------------|
| **P0-Critical** | 会导致系统故障、数据丢失、安全漏洞的问题 | 24 小时内修复 | SQL 注入、内存泄漏、硬编码密钥、空指针崩溃        |
| **P1-High**     | 影响核心功能、性能严重下降、违反强制规范 | 本周内修复    | Service 直接调 Mapper、未加事务、缓存雪崩风险 |
| **P2-Medium**   | 影响代码质量、可维护性、存在潜在风险   | 本月内修复    | 魔法值硬编码、日志占位符缺失、重复代码            |
| **P3-Low**      | 轻微优化建议、风格问题、文档缺失     | 排期优化     | JavaDoc 缺失、变量命名不规范、import 未优化  |

### 分析深度要求

- **每个 P0/P1 问题**必须提供：代码片段 + 详细分析 + 完整解决方案
- **每个 P2 问题**必须提供：代码片段 + 分析 + 修复建议
- **每个 P3 问题**至少提供：问题描述 + 优化建议
- **每个组件特性建议**必须提供：当前用法扫描结果 + 具体应用位置 + 代码示例 + 预期收益
- 单个模块发现超过 5 个问题，需单独输出子章节

### 组件特性分析约束

- **必须基于实际代码扫描**：不允许虚构项目对组件的使用方式
- **必须结合版本特性**：搜索该组件当前依赖版本的 Release Notes，不盲目推荐超前版本特性
- **必须有具体应用场景**：不允许泛泛而谈，必须指出 "在 carlos-xxx 模块的 yyy 功能中可以使用"
- **必须评估投入产出**：对每条特性建议标注实施难度和预期收益
- **优先推荐 "低投入高回报" 的特性**：如配置项开启、注解替换、API 升级等

### 特殊场景处理

- **无新 Commit**: 仍需基于当前代码全量扫描，报告标注 "今日无代码变更，基于最新 Commit xxx 扫描"
- **新增模块**: 优先深度扫描新增模块，标记为 "新增模块重点审查"
- **大规模重构**: 若发现某模块正在被大规模重构，可标注 "该模块处于重构期，部分问题可能已被识别"
- **网络不可用**: web_search 步骤失败时，跳过技术趋势和组件特性搜索，基于已知知识输出报告，并在报告中标注 "
  网络不可用，组件特性分析基于本地知识库"
