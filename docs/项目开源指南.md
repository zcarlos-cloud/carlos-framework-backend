# Carlos Framework 项目开源指南

本指南将帮助你将 Carlos Framework 从内部项目顺利转化为一个规范、健康、可持续运营的开源项目，并分别在 GitHub（面向全球）和
Gitee（面向中文开发者）上发布与维护。

---

## 📋 前置条件

在开始开源之前，请确认以下条件已经具备：

1. **GitHub 账号**：用于托管主仓库，访问 [github.com](https://github.com)。
2. **Gitee 账号**：用于中文镜像与中文社区运营，访问 [gitee.com](https://gitee.com)。
3. **本地 Git 环境**：已配置用户名、邮箱和 SSH/GPG 密钥。
4. **仓库管理员权限**：能够对仓库进行可见性、分支保护和 Secrets 配置等操作。
5. **已通过内部合规/安全/法务评审**：确保代码中不包含敏感信息、内部密钥、员工信息或公司专有资产。

## 🚀 第一步：创建并公开 GitHub 仓库

### 选项 A：将现有私有仓库转为公开

如果 Carlos Framework 已经托管在 GitHub 私有仓库中：

1. 进入 GitHub 仓库页面。
2. 点击 **Settings > General > Danger Zone**。
3. 点击 **Change visibility**，选择 **Make public**。
4. 按提示输入仓库名称并确认。

> ⚠️ **重要提示**：在更改可见性之前，请务必：
> - 扫描并清理提交历史中的密码、Token、IP 地址、内网域名等敏感信息。
> - 检查 `.gitignore` 是否正确排除了 IDE 配置、本地环境文件和构建产物。
> - 建议先使用 [git-filter-repo](https://github.com/newren/git-filter-repo) 或 BFG Repo-Cleaner 清理历史。

### 选项 B：新建公开仓库并推送现有代码

1. 访问 [github.com/new](https://github.com/new)。
2. 填写仓库信息：
    - **Repository name**：`carlos-framework`
    - **Description**：`基于 Spring Boot 4.x 与 Spring Cloud Alibaba 的企业级 Java 微服务脚手架框架`
    - **Visibility**：`Public`
    - **Initialize this repository with**：全部取消勾选（我们将推送已有代码）。
3. 点击 **Create repository**。
4. 在本地项目根目录执行：

```bash
# 若本地尚未初始化 Git
git init
git add .
git commit -m "chore: initial open source release"
git branch -M main
git remote add origin https://github.com/your-org/carlos-framework.git
git push -u origin main
```

## 🇨🇳 第二步：创建 Gitee 镜像仓库（强烈推荐）

Gitee 是国内开发者访问速度更快的中文代码托管平台，建议作为主仓库的中文镜像与中文社区运营阵地。

### 手动创建镜像

1. 登录 [gitee.com](https://gitee.com)。
2. 点击右上角 `+` > **新建仓库**。
3. 填写信息：
    - **仓库名称**：`carlos-framework`
    - **仓库介绍**：参考 `README-CN.md` 中的中文描述。
    - **是否开源**：选择 **开源**。
    - **初始化仓库**：取消勾选所有初始化选项。
4. 添加 Gitee 为第二个远程仓库：

```bash
# 添加 Gitee 远程地址
git remote add gitee https://gitee.com/your-org/carlos-framework.git

# 首次推送
git push gitee main

# 后续双平台推送
git push origin main
git push gitee main
```

### 自动同步方案（推荐）

为避免手动同步遗漏，建议通过 GitHub Actions 自动将主仓库同步到 Gitee：

- 使用 [hub-mirror-action](https://github.com/Yikun/hub-mirror-action) 等成熟 Action。
- 在 Gitee 配置 SSH 公钥，或在仓库 Secrets 中配置 `GITEE_PRIVATE_KEY`。
- 触发方式可设置为 `push` 到 `main` 分支时自动触发，或每日定时同步。

> 同步内容应至少包含 `main` 分支与所有标签（tags）。文档站点若部署在独立分支（如 `gh-pages`），也应一并同步。

## ⚙️ 第三步：配置仓库基础设置

### GitHub 仓库设置

#### 1. 分支保护规则

进入 **Settings > Branches**，为关键分支添加保护规则：

**`main` 分支**：

- ✅ **Require a pull request before merging**：合并前必须经过 PR。
- ✅ **Require approvals**：至少 1-2 人审批。
- ✅ **Dismiss stale PR approvals when new commits are pushed**：新提交后旧审批自动失效。
- ✅ **Require status checks to pass before merging**：要求 CI 检查通过，建议至少包含：
    - `build`
    - `static-analysis`
    - `code-coverage`
- ✅ **Require conversation resolution before merging**：所有讨论解决后才能合并。
- ✅ **Require signed commits**（可选但推荐）：要求提交签名。
- ✅ **Do not allow bypassing the above settings**：即使是管理员也不能绕过规则。

**`develop` 分支**：

- 规则与 `main` 类似，但审批人数和状态检查要求可适当放宽。

#### 2. Issue 与讨论区配置

- 启用 Issues：Settings > General > Features > Issues。
- 启用 Discussions：Settings > General > Features > Discussions。
- 确认 `.github/ISSUE_TEMPLATE/` 目录下的 Bug 报告、功能请求和配置模板已就绪。
- 在 Discussions 中创建置顶分类，例如：
    - 📢 发布公告
    - 💡 功能建议
    - ❓ 问答互助
    - 🚀 使用交流

#### 3. 安全与漏洞管理

进入 **Settings > Security**：

- ✅ Enable vulnerability alerts（启用依赖漏洞告警）。
- ✅ Enable secret scanning（启用密钥泄漏扫描）。
- ✅ Enable code scanning（启用代码安全扫描）。
- 配置 Dependabot：Settings > Security > Dependabot alerts。
- 确保根目录 `SECURITY.md` 文件包含漏洞报告流程和联系方式。

#### 4. 仓库元数据与 Topics

在仓库主页右侧编辑仓库信息，添加 Topics：

```text
java, spring-boot, spring-cloud, spring-cloud-alibaba, microservices,
mybatis-plus, redis, oauth2, national-cryptography, sm2, sm4,
framework, starter, multi-tenant, open-source
```

#### 5. 仓库描述

建议描述：

```text
Carlos Framework - 基于 Spring Boot 4.x 与 Spring Cloud Alibaba 的企业级 Java 微服务脚手架框架，提供 22+ Starter、OAuth2 认证、多级缓存、国密加密、工作流、AI 集成等能力。
```

### Gitee 仓库设置

配置逻辑与 GitHub 基本一致，额外注意：

1. 设置仓库为 **开源**。
2. 配置与 GitHub 对应的分支保护规则。
3. 启用 Gitee 的 Issue、PR 和 Wiki 功能。
4. 若使用 Gitee Pages 部署中文文档，可在仓库设置中启用 Pages 服务。

## 🔄 第五步：验证 CI/CD 工作流

Carlos Framework 是一个包含 55+ 模块的多模块 Maven 项目，CI/CD 的稳定性至关重要。

### 检查工作流运行状态

1. 推送代码后，进入 GitHub 仓库的 **Actions** 标签页。
2. 确认以下工作流能够正常触发并运行：
    - Maven 全量构建（含单元测试）。
    - 代码风格检查（Checkstyle/Spotless）。
    - 静态代码分析（SonarQube / SpotBugs）。
    - 代码覆盖率上报（JaCoCo + Codecov）。
3. 检查工作流日志，修复首次运行暴露的环境或配置问题。

### 必要 Secrets 配置

进入 **Settings > Security > Secrets and variables > Actions**，配置以下密钥：

| Secret              | 用途                               |
|---------------------|----------------------------------|
| `GITHUB_TOKEN`      | GitHub 自动提供，用于发布 Release、评论 PR 等 |
| `CODECOV_TOKEN`     | 代码覆盖率上报至 Codecov                 |
| `SONAR_TOKEN`       | SonarQube/SonarCloud 静态分析        |
| `GITEE_PRIVATE_KEY` | 自动同步到 Gitee 的 SSH 私钥             |
| `NEXUS_USERNAME`    | 部署 Maven 构件到私有 Nexus（如有）         |
| `NEXUS_PASSWORD`    | 对应 Nexus 密码或 Token               |
| `DOCKER_USERNAME`   | 构建并推送 Docker 镜像（如有）              |
| `DOCKER_PASSWORD`   | 对应 Docker Hub 密码或 Token          |

    - 示例配置文件。

## 🔧 第九步：长期维护与社区治理

### 日常维护任务

- [ ] 每日/每周：审阅并回复新 Issues 和 Discussions。
- [ ] 每日/每周：审阅并合并高质量 PR。
- [ ] 每周：检查 Dependabot 依赖更新建议。
- [ ] 每周：检查安全告警与 CVE 通报。
- [ ] 每月：清理过期/无效的 Issue 和 PR。

### 月度维护任务

- [ ] 评估社区健康度报告与流量趋势。
- [ ] 规划版本迭代 Roadmap。
- [ ] 更新依赖版本并发布补丁版本（如有必要）。
- [ ] 整理贡献者名单并更新 `AUTHORS.md`。

### 版本发布流程

1. 在 `develop` 分支完成新功能或缺陷修复。
2. 更新 `pom.xml` 中的版本号（使用 `${revision}` 占位符统一修改）。
3. 更新 `CHANGELOG.md`，按类型归类变更。
4. 创建 Release PR，合并到 `main`。
5. 打 Tag 并触发 Release 工作流。
6. 同步 Tag 与代码到 Gitee。
7. 在 GitHub/Gitee 发布公告，并在社区渠道传播。

### GitHub：以英文为主

- `README.md` 使用英文。

- `README-CN.md` 作为 Gitee 主展示文档。

- 可设置中文 Issue 标签，例如：`缺陷`、`功能`、`文档`、`求助`。

- 代码注释、Javadoc 统一使用英文。

## 🛡️ 安全与合规注意事项

### 对维护者

1. **禁止直接向 `main` 推送代码**：所有变更通过 PR 合并。
2. **审查所有新增依赖**：关注许可证兼容性与已知漏洞。
3. **及时响应安全告警**：CVE 披露后应在合理时间内评估影响。
4. **最小权限原则**：仅向核心维护者开放管理员权限。
5. **定期审计提交者权限**：移除长期不活跃或已离职的贡献者权限。

### 对贡献者

1. **禁止提交任何密钥、密码或内部配置**：使用环境变量或外部配置中心。
2. **输入必须校验**：防止 SQL 注入、XSS、命令注入等常见攻击。
3. **遵循 `SECURITY.md` 中的安全开发规范**。
4. **发现漏洞请通过私密渠道上报**，不要在公开 Issue 中披露。

### 开源合规检查清单

开源前，请完成以下检查：

- [ ] 所有依赖许可证与项目主许可证兼容。
- [ ] 代码中不存在公司内部域名、IP、邮箱、工号等信息。
- [ ] 已清理历史提交中的敏感信息。
- [ ] `LICENSE` 文件已明确授权条款。
- [ ] 所有第三方资源（图标、字体、文档图片）已获得使用授权。
- [ ] 若面向中国用户，文档站点需完成 ICP 备案（如部署在国内服务器）。

## ❓ 常见问题排查

| 问题                  | 可能原因                        | 解决方案                                   |
|---------------------|-----------------------------|----------------------------------------|
| GitHub Actions 构建失败 | JDK/Maven 版本不匹配或 Secrets 缺失 | 检查工作流日志，确认 `JAVA_VERSION` 和 Secrets 配置 |
| 覆盖率上报失败             | `CODECOV_TOKEN` 无效或缺失       | 在仓库 Secrets 中重新配置有效 Token              |
| Gitee 同步失败          | SSH 密钥未配置或权限不足              | 检查 Gitee 公钥与 GitHub Secrets 私钥是否配对     |
| 推送被拒绝               | 分支保护规则限制                    | 使用 PR 流程，不要直接推送到受保护分支                  |
| Issue/PR 无人响应       | 维护者时间不足                     | 建立社区志愿者机制，使用机器人自动标记和分流                 |
