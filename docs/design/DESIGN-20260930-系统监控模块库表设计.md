## 1. 设计总览

### 1.1 存储分层

| 存储 | 内容 | 访问方式 |
|------|------|----------|
| PostgreSQL（框架主库） | 实例注册、分组授权、告警规则/记录、分析报告、SQL 历史、脱敏规则（共 11 张表） | MyBatis-Plus，Manager 层 |
| ClickHouse | 指标时序点、小时聚合、Redis 慢日志、DB 慢 SQL（4 个对象） | 原生 Client，JSONEachRow 批量写（复用 audit 写入模式） |

### 1.2 命名与字段规范（对齐框架既有约定）

- 表名小写下划线，统一前缀 `monitor_`；
- 主键 `id BIGINT`（MyBatis-Plus `ASSIGN_ID` 雪花 ID），无统一 BaseEntity，公共字段各表平铺；
- 公共审计字段：`create_by BIGINT`、`create_time TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP`、`update_by BIGINT`、`update_time TIMESTAMP`（可空）；
- 逻辑删除 `is_deleted SMALLINT NOT NULL DEFAULT 0`（实体 `Boolean` + `@TableLogic`）；流水/报告类表同样保留逻辑删除字段；
- 枚举字段 PostgreSQL 侧用 `VARCHAR`（字典编码字符串，如 `REDIS_STANDALONE`）或 `SMALLINT`（状态类），开关用 `BOOLEAN`；
- 索引命名：唯一 `uk_表_字段`、普通 `idx_表_字段`；
- 不使用外键、不使用存储过程；金额无，数值阈值用 `DECIMAL(18,4)`；
- 表与字段注释：表后 `COMMENT ON TABLE/COLUMN ... IS '...'`。

### 1.4 ER 关系（文字描述）

```
monitor_instance_group 1───n monitor_instance 1───n monitor_instance_app_rel
        │                        │
        │ 1───n monitor_group_auth（role_id 关联 sys 角色，逻辑关联不建外键）
        │                        ├───n monitor_data_mask_rule（可空 instance_id=全局规则）
        │                        ├───n monitor_bigkey_report 1───n monitor_bigkey_report_item
        │                        ├───n monitor_db_capacity_snapshot
        │                        ├───n monitor_sql_history
        │                        └───n monitor_alarm_record n───1 monitor_alarm_rule 1───n monitor_alarm_silence
```

CK 侧各表通过 `instance_id` 与 PG 的 `monitor_instance` 逻辑关联（雪花 ID → UInt64）。

### 3.2 monitor_metric_point_hourly 小时聚合（物化视图预聚合）

```sql
CREATE TABLE IF NOT EXISTS monitor_metric_point_hourly
(
    instance_id   UInt64,
    metric_source LowCardinality(String),
    metric_name   LowCardinality(String),
    node          String DEFAULT '',
    hour          DateTime                      COMMENT '小时整点',
    avg_value     AggregateFunction(avg, Float64),
    max_value     AggregateFunction(max, Float64),
    min_value     AggregateFunction(min, Float64),
    p95_value     AggregateFunction(quantile(0.95), Float64),
    point_count   AggregateFunction(count, UInt64)
)
ENGINE = AggregatingMergeTree()
PARTITION BY toYYYYMM(hour)
ORDER BY (instance_id, metric_name, hour)
TTL hour + INTERVAL 90 DAY
SETTINGS index_granularity = 8192;

CREATE MATERIALIZED VIEW IF NOT EXISTS monitor_metric_point_hourly_mv
TO monitor_metric_point_hourly
AS SELECT
    instance_id,
    metric_source,
    metric_name,
    node,
    toStartOfHour(ts) AS hour,
    avgState(value)   AS avg_value,
    maxState(value)   AS max_value,
    minState(value)   AS min_value,
    quantileState(0.95)(value) AS p95_value,
    countState()      AS point_count
FROM monitor_metric_point
GROUP BY instance_id, metric_source, metric_name, node, hour;
```

> 查询侧使用 `-Merge` 组合函数（`avgMerge(avg_value)` 等）。查询封装在 `ClickHouseQueryClient` 同款的 Monitor 查询客户端中，SQL 固化在代码内，不对外暴露。

## 6. 设计说明与取舍

1. **ID 用 BIGINT 雪花**：与 sys_menu/sys_dict 新表风格一致（AGENTS.md 中 char(32) 为旧 MySQL 规约，PostgreSQL 实际落地为 BIGINT 雪花）；CK 侧对应 `UInt64`。
2. **凭据只存密文**：`password_cipher` 为 SM4 加密结果，任何 VO/日志不输出该字段；连接测试接口不回显。
3. **告警记录冗余 rule_name / instance_name**：规则改名、实例删除后历史记录仍可读。
4. **大 key 报告明细进 PG 而非 CK**：单报告 ≤500 条，属于报告型数据，PG 查询/关联更方便；CK 留给高频时序。
5. **慢 SQL 指纹入 CK**：采集周期内聚合写入，避免逐条高基数写 PG；指纹 = Druid SQL 归一化后哈希，与采集侧共用算法。
6. **tags 用 CK `Map(String,String)`**：兼容不同来源指标的标签差异（如 db 编号、slot、会话状态），避免宽表膨胀。
7. **不建外键**：遵循框架规约，关联一致性由 Manager 层保证。
