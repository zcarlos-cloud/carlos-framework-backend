## 1. 背景与目标

Carlos Framework 定位为**通用基础框架**。经全仓盘点（2026-09-22），框架在审计、数据权限、消息渠道、代码生成、API 文档等方面已较完整，但对照主流管理框架（RuoYi-Vue / Soybean / SpringBlade 系）仍有若干硬缺口。本计划给出补齐路线图与每个阶段的落地方案。

### 1.1 已有能力（不重复建设）

| 能力 | 位置 |
|---|---|
| 操作日志/审计（ClickHouse + 归档 + 导出） | carlos-audit |
| 数据权限（SpEL + MyBatis 拦截器） | carlos-spring-boot-starter-datascope |
| 接口权限（@PreAuthorize + PermissionEvaluator） | carlos-spring-boot-starter-security |
| 消息四渠道（短信/邮件/钉钉/WebSocket）+ 已读回执 | carlos-message |
| 代码生成器（GUI 工具） | carlos-tools |
| API 文档（Knife4j + 网关聚合） | carlos-spring-boot-starter-openapi |
| 分布式 ID（雪花） | carlos-spring-boot-starter-snowflake |
| 参数配置 / 字典(缓存) / 国际化 / 区域(导入导出) / 菜单·操作·路由 / 文件存储 | carlos-system |

### 1.2 缺口总览

| 优先级 | 缺口 | 阶段 |
|---|---|---|

## 2. 总体路线图

```
S1 定时任务平台 ──┐
S2 租户管理    ──┼── 相互独立，可并行；建议按 S1→S2→S3→S4→S5→S6 顺序交付
S3 公告       ──┤    （S1/S2 无依赖；S3 可选依赖 carlos-message 推送；
S4 登录日志    ──┤     S4 依赖 auth token 存储现状；S5 独立工具；
S5 序列号      ──┤     S6 依赖 S1 的调度能力做监控采集/任务清理）
S6 增强项     ──┘
```

每个阶段的公共交付物（**每阶段必须包含，勿遗漏**）：

1. 后端：api / bus 层代码（遵循 `{module}-api` + `{module}-bus` 结构）
2. 数据库：建表/迁移 SQL（幂等，写死 ID 的菜单独列回滚脚本）
3. **网关路由**：`carlos-gateway` 显式新增路由（框架非显性约定：不加路由请求到不了服务）
4. **前端页面**：carlos-framework-ui 页面 + `src/service/api/*.ts` + `sys_menu` 迁移 SQL（UPDATE 保 ID 或幂等 INSERT）
5. **测试**：模块 pom 覆盖 `skipTests=false`（父 POM 写死跳过，任何 `-D` 打不开），MockMvc 接口测试
6. 文档：模块 README / docs 更新

### 编码规范红线（所有阶段通用）

- 严禁 Service 层直接操作 Redis（在 Manager 层）
- 严禁直接编写 SQL（MyBatis-Plus + mybatis-plus-join）
- 异常用 `ServiceException`，不用 `RuntimeException`
- 枚举实现 `BaseEnum` + `@AppEnum`
- 属性注入用 `@ConfigurationProperties`，禁用 `@Value`
- 不可变性原则：创建新对象，不修改原对象
- 类名必须 import，禁止全限定名

## 3. S1 定时任务调度平台（P0）

### 3.1 现状与问题

- 全仓库无 quartz / xxl-job 依赖，无 Job 表/管理页面
- 散落 `@Scheduled`：audit 归档、message 重试/健康检查/配置刷新 —— 无法统一启停、查看执行日志、动态调 cron

### 3.2 技术选型

| 方案 | 结论 |
|---|---|
| **Quartz JDBC Store** | ✅ **选用**。集群安全（数据库锁）、无额外中间件、与 PostgreSQL 契合、Spring Boot 原生集成 |
| xxl-job | ❌ 需独立调度中心服务，运维成本高 |
| 自研 DB 轮询调度 | ❌ 重复造轮子，集群协调复杂 |

### 3.3 模块归属

新建 **`carlos-job`** 业务模块（标准四层：`carlos-job-api` / `carlos-job-bus` / `carlos-job-boot` / `carlos-job-cloud`），作为独立微服务管理全框架调度任务；各业务模块通过 Feign/`JobClient` 注册任务处理器。

备选：并入 carlos-system。**建议独立模块** —— 调度是横切能力，后续所有模块都会依赖，独立部署便于集中管控。

### 3.4 表设计（除 Quartz 自带的 11 张 `qrtz_*` 表外）

```sql
-- 任务执行日志
CREATE TABLE job_execution_log (
    id              BIGSERIAL PRIMARY KEY,
    job_name        VARCHAR(128) NOT NULL,   -- 任务标识
    job_group       VARCHAR(64)  NOT NULL DEFAULT 'DEFAULT',
    trigger_type    SMALLINT     NOT NULL,   -- 1-cron 2-固定间隔 3-手动触发
    cron_expression VARCHAR(64),
    status          SMALLINT     NOT NULL,   -- 1-成功 2-失败 3-执行中
    start_time      TIMESTAMP    NOT NULL,
    end_time        TIMESTAMP,
    duration_ms     BIGINT,
    error_message   TEXT,
    server_node     VARCHAR(64),             -- 执行节点（集群下定位）
    tenant_id       BIGINT       NOT NULL DEFAULT 0,
    create_time     TIMESTAMP    NOT NULL DEFAULT now()
);
CREATE INDEX idx_job_log_name_time ON job_execution_log (job_name, start_time DESC);
```

任务定义本身用 Quartz 的 `qrtz_job_details` 持久化，**不重复建任务表**；管理接口直接操作 Scheduler API。

### 3.5 接口设计（`/job/**`）

| 端点 | 说明 |
|---|---|
| `GET /job/page` | 任务分页（名称/组/状态筛选） |
| `POST /job/create` | 新建任务（beanName + cron + 参数 JSON） |
| `PUT /job/update` | 修改 cron/参数 |
| `POST /job/pause` / `/job/resume` | 暂停 / 恢复 |
| `POST /job/run-once` | 手动触发一次 |
| `DELETE /job/delete` | 删除 |
| `GET /job/log/page` | 执行日志分页 |

### 3.6 任务处理器约定

```java
public interface JobHandler {
    void execute(String params) throws Exception;  // params 为任务配置里的 JSON 字符串
}
```

业务模块实现 `JobHandler` 并注册为 Spring Bean，任务配置中填 beanName。框架提供 `JobExecutionLogListener`（Quartz TriggerListener）自动落执行日志。

### 3.7 存量迁移

S1 落地后，将 audit 归档、message 各 `@Scheduled` 迁移为受管任务（保留开关配置，可回退）。

### 3.8 前端页面

管理后台新增「系统管理 → 定时任务」：任务列表（启停/执行/日志抽屉）+ 执行日志页。菜单 SQL 幂等插入。

### 3.9 任务清单

- [ ] 新建 carlos-job 四层模块骨架（用 carlos-module-scaffolder）
- [ ] 引入 quartz + JDBC Store 配置（PostgreSQL 建表脚本，Quartz 官方提供）
- [ ] JobHandler 接口 + JobExecutionLogListener + 执行日志 CRUD
- [ ] 管理 Controller（3.5 全部端点）
- [ ] 网关路由 `Path=/job/**`
- [ ] 前端页面 + 菜单 SQL
- [ ] surefire 覆盖 + MockMvc 测试
- [ ] 存量 @Scheduled 迁移方案文档（不强制本阶段迁移）

### 3.10 风险

- **中**：Quartz 集群模式下各 boot 单体与 cloud 微服务并存，需确认任务只在 job 服务执行（业务 Handler 通过 Feign 回调业务模块，避免在每个节点重复执行）
- **低**：Quartz 表与业务表同库，注意 `tenant_id` 拦截器不要拦截 `qrtz_*` 表

## 4. S2 租户管理（P0）

### 4.1 现状与问题

- org 模块有 `OrgTenantLineHandler`（MyBatis-Plus TenantLineHandler），硬编码隔离 10 张 org 表
- `tenantId` 来自 `UserContext`，但**没有租户表**：租户是谁、是否停用、如何开通，全部无管理

### 4.2 表设计

```sql
CREATE TABLE org_tenant (
    id           BIGSERIAL PRIMARY KEY,
    tenant_code  VARCHAR(32)  NOT NULL UNIQUE,   -- 租户编码（登录时选择）
    tenant_name  VARCHAR(128) NOT NULL,
    contact_name VARCHAR(64),
    contact_phone VARCHAR(32),
    status       SMALLINT     NOT NULL DEFAULT 1, -- 1-正常 2-停用（枚举 BaseEnum）
    expire_time  TIMESTAMP,                        -- NULL 表示永不过期
    remark       VARCHAR(512),
    create_time  TIMESTAMP    NOT NULL DEFAULT now(),
    update_time  TIMESTAMP    NOT NULL DEFAULT now(),
    deleted      SMALLINT     NOT NULL DEFAULT 0
);
```

> 租户属于组织域，归属 `carlos-org`（表前缀 `org_`，与现有 org_user 等一致）。**0 号租户保留为平台租户**（现有数据默认 0，与 TenantLineHandler 的默认值对齐）。

### 4.3 接口设计（`/org/tenant/**`）

标准 CRUD + `POST /org/tenant/change-status`（停用/启用）+ `POST /org/tenant/init-admin`（为新租户初始化管理员账号，复用 org_user 创建逻辑，tenantId=新租户）。

### 4.4 关键改造点

1. **停用校验**：登录时校验租户状态/有效期（auth 登录流程加租户检查，停用租户拒绝登录）
2. **登录带租户**：登录接口增加 `tenantCode` 参数（可选，默认 0），`UserContext` 写入真实 tenantId
3. **隔离范围治理**：`OrgTenantLineHandler.TENANT_TABLES` 硬编码集合改为**从配置表或 @ConfigurationProperties 读取**，避免每加一张租户表都改代码
4. **超管跨租户**：平台租户（0）管理员可切换查看任意租户数据（ TenantLineHandler 对超管放行）

### 4.5 前端页面

「组织管理 → 租户管理」：租户列表 + 新增租户（同时初始化管理员）+ 停用/启用。登录页加租户编码输入（可配置开关）。

### 4.6 任务清单

- [x] `org_tenant` 建表 SQL + 实体/Mapper/Manager/Service/Controller（2026-09-22 完成，DDL 见 `carlos-org/docs/sql/org_tenant.sql`，主键改为雪花 BIGINT、唯一索引改部分索引 `WHERE is_deleted = 0`）
- [x] 登录流程租户校验（auth 侧改动，`TenantLoginChecker` 三入口共用：直登 `/auth/user/login`、`/oauth2/token`、OIDC formLogin）
- [x] TENANT_TABLES 配置化改造（`OrgProperties.tenant.tables/platform-tenant-id/super-admin-ignore`，`OrgTenantLineHandler` 改为配置驱动）
- [x] 超管跨租户放行（`superAdminIgnore` 开关，默认 false）
- [x] 前端页面 + 登录页租户输入 + 菜单 SQL（`/org/tenant` 页 + 登录页租户编码由 `VITE_AUTH_TENANT_ENABLED` 控制，菜单 SQL `docs/sys_menu_tenant_migration.sql`）
- [x] 网关无需新路由（走已有 `/org/**`）

### 4.7 风险

- **高**：登录流程改动影响面大，需回归 OIDC/普通登录全链路；建议 feature flag 控制租户校验开关
- **中**：存量数据 tenant_id=0 的语义固化，文档明确「0=平台租户」

## 5. S3 公告/站内通知（P1）

### 5.1 现状

`carlos-system-api` 有 `SysNewsAO` / `SysNewsDetailAO` 两个孤儿类（无表无实现）。

### 5.2 方案选型

**方案 A（推荐）：在 carlos-system 补齐公告管理**，WebSocket 推送复用 carlos-message。
公告与业务消息语义不同（公告是运营发布、全员/按角色可见、有置顶和有效期），不适合塞进 message 的发送队列模型。

### 5.3 表设计

```sql
CREATE TABLE sys_news (
    id           BIGSERIAL PRIMARY KEY,
    title        VARCHAR(256) NOT NULL,
    news_type    SMALLINT     NOT NULL DEFAULT 1,  -- 1-公告 2-通知 3-更新日志（BaseEnum）
    content      TEXT         NOT NULL,             -- 富文本
    publish_scope SMALLINT    NOT NULL DEFAULT 1,  -- 1-全员 2-指定角色
    scope_role_ids VARCHAR(512),                    -- JSON 数组，scope=2 时生效
    is_top       BOOLEAN      NOT NULL DEFAULT FALSE,
    status       SMALLINT     NOT NULL DEFAULT 1,  -- 1-草稿 2-已发布 3-已下线
    publish_time TIMESTAMP,
    expire_time  TIMESTAMP,
    tenant_id    BIGINT       NOT NULL DEFAULT 0,
    create_by    BIGINT, create_time TIMESTAMP NOT NULL DEFAULT now(),
    update_by    BIGINT, update_time TIMESTAMP NOT NULL DEFAULT now(),
    deleted      SMALLINT     NOT NULL DEFAULT 0
);

-- 已读记录（用户维度）
CREATE TABLE sys_news_read (
    id          BIGSERIAL PRIMARY KEY,
    news_id     BIGINT NOT NULL,
    user_id     BIGINT NOT NULL,
    read_time   TIMESTAMP NOT NULL DEFAULT now(),
    tenant_id   BIGINT NOT NULL DEFAULT 0,
    CONSTRAINT uk_news_user UNIQUE (news_id, user_id)
);
CREATE INDEX idx_news_read_user ON sys_news_read (user_id, news_id);
```

### 5.4 接口设计（`/sys/news/**`）

管理端：CRUD + 发布/下线 + 分页。
用户端：`GET /sys/news/my/page`（我可见的公告，含已读状态）、`POST /sys/news/read?id=`（标记已读）、`GET /sys/news/unread-count`（顶栏铃铛角标）。
发布时可选调用 carlos-message WebSocket 推送实时提醒（配置开关，S3 一期可只做拉取）。

### 5.5 前端页面

## 6. S4 登录日志 / 在线用户 / 踢下线（P1）

### 6.1 现状

- 登录事件已进 carlos-audit（ClickHouse），但无面向运维的登录日志查询页
- auth 有 TokenController（`/logout`、`/delete` 删 token）、登录失败锁定（LoginAttemptManager）、安全告警（SecurityAlert），但无在线用户列表

### 6.2 方案

**登录日志**：不新建表。在 auth 模块提供 `/auth/login-log/page` 接口，内部走 carlos-audit 的查询 Feign（logType=登录），避免双写。
**在线用户**：token 存于 Redis（auth 已有），新增 Manager 扫描在线 token 键，聚合用户/登录时间/IP/设备，提供 `/auth/online-user/page` + `POST /auth/online-user/kick`（批量删 token = 踢下线）。

> **2026-09-23 实施完成**。调研结论（对应 6.5 风险）：token 是**有状态**的（全量落 Redis，网关走内省判效），
> 在线用户/踢下线直接可行，无需会话注册表。落地要点：
> - 在线用户数据源：`oauth2:user_sessions:{username}` 索引 + `oauth2:id:{authId}` 授权 JSON；
>   IP/UA 不在 token 里 ⇒ 新增 `oauth2:session_meta:{authId}`（`RedisOAuth2AuthorizationService.save()` 首次签发时写入、remove 级联删）
> - 踢下线 = 删授权记录 + **同步删网关内省缓存** `token:introspection:{sha256(token)}`（否则最长延迟 5 分钟）
> - 登录日志固定 `logType=USER_LOGIN`（成功/失败靠 logStatus 区分）；audit-api 补了 `principalName` 透传
> - 网关零改动（`/auth/**` 既有路由）；**本机无 ClickHouse ⇒ 登录日志页恒空（同审计页）**

### 6.3 接口设计

| 端点 | 说明 |
|---|---|
| `GET /auth/login-log/page` | 登录日志分页（账号/IP/结果/时间范围） |
| `GET /auth/online-user/page` | 在线用户分页 |
| `POST /auth/online-user/kick` | 踢下线（支持批量、按 userId） |

### 6.4 前端页面

「系统管理 → 在线用户」（含踢下线按钮）、「系统管理 → 登录日志」。

### 6.5 风险

- **中**：在线用户依赖 token 在 Redis 的键结构，需先确认实际 key 格式与 TTL；若 token 为无状态 JWT 则需引入会话注册表，工作量升级 —— **实施第一步先调研 token 存储形态**

## 7. S5 业务编码/序列号生成器（P1）

### 7.1 现状

只有雪花分布式 ID，无规则化业务编码（如 `PO20260922-0001`）。

### 7.2 方案

在 **carlos-system** 新增序列号域（基础数据服务属性），Redis 原子自增实现：

```sql
CREATE TABLE sys_sequence_rule (
    id            BIGSERIAL PRIMARY KEY,
    rule_code     VARCHAR(64) NOT NULL UNIQUE,  -- 业务编码，如 order_no
    rule_name     VARCHAR(128) NOT NULL,
    prefix        VARCHAR(32),                   -- 前缀，如 PO
    date_pattern  VARCHAR(32),                   -- 日期段，如 yyyyMMdd；NULL 不含日期
    seq_length    INT         NOT NULL DEFAULT 6, -- 流水位数
    step          INT         NOT NULL DEFAULT 1,
    reset_cycle   SMALLINT    NOT NULL DEFAULT 2, -- 1-永不重置 2-按日 3-按月 4-按年
    current_value BIGINT      NOT NULL DEFAULT 0, -- 仅作展示/兜底，真实计数在 Redis
    tenant_id     BIGINT      NOT NULL DEFAULT 0,
    create_time TIMESTAMP NOT NULL DEFAULT now(),
    update_time TIMESTAMP NOT NULL DEFAULT now(),
    deleted       SMALLINT    NOT NULL DEFAULT 0
);
```

生成逻辑（Manager 层）：Redis key = `seq:{ruleCode}:{datePart}`，INCRBY step，按 reset_cycle 设 TTL；格式化为 `prefix + datePart + 左补零流水`。Redis 不可用时降级数据库行锁自增（SELECT ... FOR UPDATE 由 MP 层封装，**不手写 SQL**，用 `QueryWrapper` + `@Lock` 或服务层 synchronized + 单条 update）。

> **2026-09-23 实施完成**。DDL 定稿见 `carlos-integration/carlos-system/docs/sql/sys_sequence_rule.sql`，
> 与设计稿有四处偏离（该文件注释里也逐条写明）：
>
> - `id` 用**雪花 ID**（`@TableId(type = IdType.ASSIGN_ID)`）而非 `BIGSERIAL`；逻辑删除列名 `is_deleted`；
>   唯一约束不用 `UNIQUE` 而是**部分唯一索引** `uk_sys_sequence_rule_code (rule_code) WHERE is_deleted = 0`
>   —— 否则逻辑删除过的规则编码无法重建。
> - 补两列：`separator VARCHAR(8) NOT NULL DEFAULT ''`（日期段与流水之间，设计稿把 `PO20260923-0001` 的 `-` 漏了）、
>   `current_period VARCHAR(32) NOT NULL DEFAULT ''`（兜底水位所属日期段，CAS 条件的一半）。
> - `current_value` 定位为**数据库兜底水位**，不是展示计数器：Redis 正常时按条件尽力回写，
>   展示会**滞后最多一次生成**（原 7.5 说「一致性仅作展示」，实际它还是 Redis 不可用时的发号依据）。
> - 无日期段（`date_pattern` 为空）时**强制 `reset_cycle = 1`**（服务层以 20984 拒绝）：编码里没有周期标识时，
>   跨周期流水归零会与上一周期编码重复。
>
> 落地要点：
>
> - **播种 + 溢出预检 + 自增 + 首次设过期，四件事在同一个 Lua 脚本内完成**（`SysSequenceRuleManagerImpl.INCR_SCRIPT`）。
>   - 播种：以「数据库水位（同日期段时）」为下限 `max(Redis 现值, 水位)` 再自增 —— Redis 丢数据/降级后不会从 0 重来重号；
>   - 溢出预检必须在**自增之前**：先自增再校验会让越界规则每次调用都把计数往前推，一条配错的规则被永久打死；
>   - 过期判断用 `TTL < 0`（`SET` 播种会清掉 TTL），不能用「返回值等于本次步长」判断首次。
> - Redis 异常时降级为**数据库 CAS 自增**（`LambdaUpdateWrapper` 以旧 `current_value`/`current_period` 为条件，
>   最多重试 5 次），未采用设计稿的 `SELECT ... FOR UPDATE`；耗尽抛 50908，绝不返回可能重复的号段。
> - 日期段格式走**白名单枚举**（`SequenceDatePatternEnum`），不把库里的字符串直接喂给 `DateTimeFormatter`。
> - Redis 键：`sys:sequence:{ruleCode}`（无日期段）或 `sys:sequence:{ruleCode}:{period}`；清理用**精确键 + 带冒号界符的 pattern**
>   （无界符的 `…:order_no*` 会连 `order_no_extra` 的计数键一起删掉，对方从 1 重发）。
> - 网关**零改动**（`/sys/**` 既有路由）；Feign 实现 `/api/sys/sequence/**` 带 `@Hidden`，
>   `nextBatch` 单次上限 1000（`ApiSequence.MAX_BATCH_SIZE`），号段对象回传 `step`（调用方按步长拆段才不会拼错集合）。
> - 前端「系统管理 → 编码规则」`src/views/manage/sequence/`；菜单 SQL
>   `carlos-framework-ui/docs/sys_menu_sequence_migration.sql`（幂等 INSERT，回滚脚本成对，已同步 `sys_menu_init.sql`）。
>
> **2026-09-23 评审修复（java-review + security-review）**——以下 5 类缺陷已修，其中第 1 条是上线级阻塞：
>
> 1. **Lua 快路径从未真正生效（致命）**：`RedisTemplate.execute(script, keys, Object... args)` 的 ARGV 是**可变参数**，
>    Java 不会把集合展开成可变参数，传 `List` 只会得到**一个** ARGV，Lua 侧 `tonumber(ARGV[1])` 为 nil ⇒ 每次生成都抛错、
>    静默退化成数据库兜底（表面能跑，Redis 白接）。且框架的值序列化器是 JSON，标量也会被写成带引号的 `"1"`。
>    修法：`RedisUtil` 新增 `lua(String script, List<String> keys, Class<T> retType, String... args)`，ARGV 走
>    `RedisSerializer.string()` 逐个下发；旧的 `(script, keys, List, Class)` 重载标记 `@Deprecated` 并委托给它（行为已修正）。
>    **影响面已核对**：全仓只有 `carlos-test/RedisController` 用另一个（本来就正确的）varargs 重载，零波及。
> 2. **TTL 短于日期段 ⇒ 周期内重号**（如 `yyyyMM` + 按日重置）：TTL 改为 `max(重置周期 TTL, 日期段周期 × 2)`，
>    并在服务层新增**不变式 20986**：重置周期不得短于日期段粒度。注意比较的是**语义时长**（周期 vs 粒度），
>    不是两个带宽限的 TTL —— 拿 2 倍粒度的 TTL 去比会把「按月日期段 + 按月重置」这种最自然的组合误判为不兼容。
> 3. **枚举越界静默落库默认值**：`resetCycle` 越界（如 99）会被解析成 null，MyBatis-Plus 的 NOT_NULL 更新策略把该列
>    **直接丢弃**、落到列默认值 2（按日）。新增 10908 显式校验 + Param 层 `@Min/@Max(4)`。
> 4. **部分更新被跨字段规则误拒**：更新参数里 null = 不改（NOT_NULL 策略）、空串 = 清空，只校验「半个对象」会让
>    「只改名称」这种请求也撞上 20984/20986。改为在「原值 + 本次改动」合并出的**完整视图**上校验。
> 5. **其它**：`step ≥ 10^seqLength` 与「新位数装不下当前水位」直接拒（否则规则打不出号）；`prefix`/`separator` 加
>    `^[A-Za-z0-9_-]*$` 字符白名单（前后端逐字同步，挡住 `%`/`_`/换行等会污染下游解析的字符）；
>    改日期段时**不做任何「重置计数」动作**（见下节第二轮复核）；`deleteRules` 加 `@Transactional`；
>    `add`/`modify` 返回 false 时抛 50909（不再静默成功）；错误消息不回显 `ruleCode`（改落日志）；
>    清计数失败/写水位失败只记日志不阻断；`SysSequenceRuleManagerImpl` 的 `e.getMessage()` 改为传异常对象（保留堆栈）。
>
> 测试：`SequenceCodeFormatterTest`(11) + `SysSequenceRuleServiceTest`(26) + `SysSequenceRuleManagerImplTest`(10) = **47 例**，
> `mvn -o test` 全模块 **76 例全绿**。其中 Manager 测试专门断言「Lua 的 ARGV 是 4 个独立标量」，是第 1 条缺陷的回归护栏
> （它用自定义 Answer 而非 matcher 打桩：`execute` 是可变参数方法，matcher 个数与实参「原样/展开」两种形态对不上，
> 很容易打成永不命中的空桩）。
>
> **2026-09-23 第二轮独立复核**（对上述修复逐条验证，CONFIRMED-OK 为主，另修 2 处 + 3 处低危）：
>
> 1. **改日期段时「先改配置、后清计数」有重号窗口（HIGH）**：`modify` 已提交而 `clearCounters` 尚未执行的窗口内，
>    用**新**规则生成的请求会给新周期键播种并发出 `X-0001`，随后清键把它删掉，下一个请求又从 1 开始 ⇒ 重号。
>    把清理前置同样不安全（窗口内读到**旧**规则的迟到请求会因水位日期段不匹配从 0 播种，发出当天早已发过的
>    `X-0001`；把日期段改回去也会重号）。故**直接取消改配置时的清理与水位重置** —— 日期段一改，新格式的日期段串
>    长度与旧串必然不同（枚举内 0/4/6/8/10/14 互不相同），新键与旧键不可能同名、数据库水位也因日期段不匹配自动失效，
>    新格式天然从 1 开始；旧键由 TTL 回收（原规则无日期段时会留下一个无读取入口的孤儿键）。`resetCounter` 已随之删除。
> 2. **数据库兜底路径缺溢出预检（MEDIUM）**：Lua 路径「预检在自增之前」，而 `nextFromDb` 直接 `base + delta` 写库，
>    越界时把该区间内**合法且从未发出**的号永久烧掉（9950 + 100 越过 9999 ⇒ 9951~9999 全丢），且水位越界后
>    Redis 恢复会以此为播种下限、此后每次生成都溢出 ⇒ 规则被无故打死。已补同口径预检（报错前不写库）。
> 3. **低危**：Lua 溢出分支原先会先 `SET`（清 TTL）再返回哨兵，留下永不过期的孤儿键 ⇒ 改为「先算基准、预检、
>    通过后才 SET」；`step < 1` 补 10909 校验（`INCRBY 0` 会反复发出同一编码，此前只靠 Param 层与未应用的 DDL CHECK）；
>    DDL 注释里 20986 的理由（「键会中途过期」）已被 TTL 取 max 推翻，更正为「配置与意图不符」（前端 i18n 同步）。
> 4. **测试**：Manager 测试补断言两个序列化器必须是 `StringRedisSerializer`（原先只守住「ARGV 是 4 个标量」，
>    改回 JSON 值序列化器时仍会假绿 —— 那正是原缺陷的另一半）；数据库兜底用例补 CAS 条件断言
>    （MP 的 `formatParam` 是惰性的，要先调 `getSqlSegment()` 实参才进 `paramNameValuePairs`）；
>    新增「数据库兜底越界不写库」用例。
