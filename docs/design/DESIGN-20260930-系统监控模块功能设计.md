## 1. 模块结构

### 1.1 Maven 模块（对齐 carlos-audit 四件套）

```
carlos-monitor/
├── pom.xml
├── carlos-monitor-api/                 # Feign 接口 + AO（供其他服务查询实例健康等）
│   └── com.carlos.monitor/
│       ├── api/                        # ApiMonitorInstance（实例健康查询）、fallback/
│       └── pojo/ao|param/
├── carlos-monitor-bus/                 # 业务实现（核心）
│   └── com.carlos.monitor/             # 按域分包，见 1.2
```

依赖规则：bus 依赖 starter-web、starter-mybatis、starter-security、starter-disruptor、starter-encrypt、starter-migration、clickhouse-jdbc、lettuce（spring-data-redis）、druid、dynamic-datasource（仅复用其数据源包装思想，不直接依赖）、nacos-client，以及 audit-api / message-api / job-api（Feign 集成）。版本全部由 carlos-dependencies 管理，严禁硬编码。

## 2. 核心链路设计

### 2.1 指标采集链路（写路径）

```
carlos-job 调度中心（cron: 按实例 collect_interval 动态注册/分片）
   │ 触发 CollectJobHandler(instanceId, collectType)
   ▼
CollectTaskRouter ──按 instance_type 路由──▶ MetricCollector（SPI）
   │                                            │ RedisMetricCollector：INFO/CLUSTER INFO/DBSIZE
   │                                            │ DbMetricCollector：Druid 池指标 + DbTypeAdapter 系统视图
   │                                            │ ServiceMetricCollector：Nacos 实例 × Actuator /metrics
   │                                            ▼
   │                                     List<MetricPoint>（含 instanceId/metricName/node/tags/value/ts）
   ▼
MetricSink.offer() ──▶ Disruptor 环形缓冲（复用 starter-disruptor，carlos.monitor.disruptor.* 配置）
                         │
                         ▼ MonitorMetricEventHandler（批量聚合 + 触发 AlarmEngine.evaluate）
                         ▼
              MonitorClickHouseWriter（双缓冲批量写，FORMAT JSONEachRow，
                                      失败落盘 logs/monitor/backup/ + 恢复重放，模式复刻 audit）
```

设计要点：

1. **采集任务不随实例数线性膨胀**：job 中心注册 N 个分片任务（默认 8 分片），每次触发按 `instanceId % N` 捞取到期实例（`collect_enabled=true AND last_collect_time + collect_interval <= now`），单任务内多实例并发采集（虚拟线程池，上限可配）。
2. **采集器 SPI**：`MetricCollector { InstanceType support(); List<MetricPoint> collect(CollectorContext ctx); }`，新中间件类型 = 新增 SPI 实现 + 字典项，不动主链路。
3. **单实例隔离**：采集全部包 try-catch，失败仅回写 `monitor_instance.health_status=DOWN` 并产出 `instance.unreachable` 指标点，不影响其他实例。
4. **健康回写节流**：health_status/last_collect_time 回写走 Manager 层 + Caffeine 合并（同实例 10s 内只写一次库），避免高频 UPDATE。
5. 慢日志类明细（slowlog/slow_sql）同链路进入 CK 明细表，与指标点共用写入器。

### 2.2 指标查询链路（读路径）

```
前端 → MonitorMetricsController
        → MetricQueryService
            ├── 实时值：Redis 缓存（Caffeine 60s + Redis 5min，键 monitor:metric:current:{instanceId}，
            │            采集成功时由 sink 侧回写，Manager 层维护）
            ├── 1h/6h：monitor_metric_point（原始点）
            └── 24h/7d/30d：monitor_metric_point_hourly（avgMerge/maxMerge/quantileMerge）
```

### 2.3 Redis 数据管理链路

```
前端 → RedisDataController（@PreAuthorize 权限点 + @MonitorAudit 审计注解）
        → RedisDataProxy（按 instanceId 从 InstanceConnectionRegistry 取连接）
            ├── 读：SCAN（游标透传，COUNT 可配）→ TYPE/TTL/(可选)MEMORY USAGE → 值读取按类型分页
            │        （DataMasker 按 monitor_data_mask_rule 对 hash field/string 内容脱敏）
            └── 写：RedisWriteGuard 前置校验（manage_enabled、权限点、高危确认标识 confirmToken）
                     → 执行（删除走 UNLINK；批量删除分批 500/批，批间 sleep 可配）
                     → 快照前值 → MonitorAuditReporter 上报 carlos-audit
```

- **禁止命令清单**：`KEYS`、`FLUSHALL`、`FLUSHDB`、`CONFIG`、`DEBUG`、`SHUTDOWN`、`MONITOR`（仅热 key 采样内部受控使用）、`SLAVEOF/REPLICAOF`、`CLUSTER` 写操作。RedisDataProxy 只暴露类型化方法，不提供"任意命令执行"入口——从设计上杜绝命令注入。
- cluster 模式：写操作经 CRC16 定位分片后路由到对应节点连接；key 浏览为各节点并行 SCAN 聚合视图。

### 2.4 SQL 控制台链路

```
前端 → SqlConsoleController（monitor:db:sql:readonly / :write）
        → SqlConsoleService
            1. 实例校验：manage_enabled；写语句还需 sql_write_enabled + :write 权限 + 高危确认
            2. SqlGuard 解析（Druid WallParser，按 dbType 选择 PG/MySql WallProvider）：
               - 单语句校验（多语句拒绝）
               - 白名单：SELECT/EXPLAIN（只读模式）；写模式追加 UPDATE/DELETE
               - UPDATE/DELETE 必须含非恒真 WHERE（WallVisitor 提取条件，恒真/空条件拒绝）
               - 黑名单：DDL、DCL、CALL、LOAD、COPY、INTO OUTFILE、危险函数（pg_terminate_backend 等）
            3. SELECT 自动包裹 LIMIT（默认 500，硬上限 5000，用户传更小值生效）
            4. DbDataProxy 执行（实例级 Druid 数据源，只读账号优先；
               写执行 setAutoCommit=false，影响行数 > 阈值（默认1万）回滚并提示）
            5. 结果集列级脱敏（monitor_data_mask_rule）→ 返回 + monitor_sql_history 落库 + 审计上报
```

### 2.5 告警链路

```
MonitorMetricEventHandler（每批指标落盘前）
   → AlarmEngine.evaluate(batch)
       1. RuleMatcher：按 metric_source + target（INSTANCE/GROUP/ALL）匹配启用规则（Caffeine 缓存规则 60s）
       2. 连续周期判定：违规计数存 Redis（monitor:alarm:violation:{ruleId}:{instanceId}，INCR + TTL=3×interval），
          达到 duration_count 才触发
       3. AlarmStateMachine：
          - 无未恢复记录 → 新建 FIRING 记录 → SilenceChecker → AlarmNotifier（carlos-message Feign）
          - 已有 FIRING/CONFIRMED → 刷新 last_trigger_time，不重复通知（收敛）
          - 指标恢复正常 → 状态→RECOVERED + recover_time + 恢复通知
   确认/静默为人工操作：AlarmRecordController（monitor:alarm:confirm / :silence 权限点）
```

## 3. 核心组件设计

### 3.1 实例连接管理（instance/connection/）

| 类 | 职责 |
|----|------|
| `CredentialCipher` | 凭据 SM4 加解密（委托 starter-encrypt），仅在本包内使用；password_cipher 不出本包明文外的任何 VO/日志 |
| `InstanceConnectionRegistry` | 实例连接池注册中心。`Guava LoadingCache<Long, ManagedConnection>`（maximumSize 可配默认 500，expireAfterAccess 30min，实例编辑/删除时显式失效）。ManagedConnection 为 sealed 接口：`RedisManaged`（Lettuce `StatefulRedisConnection` + cluster 变体 + 可选 RedissonClient）/ `DbManaged`（Druid `DruidDataSource`，按库名+账号创建，maxActive 默认 8，monitor 专用小池） |
| `InstanceConnectionTester` | 连接测试：Redis→PING/INFO 返回版本与角色；cluster→各节点 PING 与 CLUSTER NODES；DB→`SELECT 1` + 版本；返回耗时与节点明细 |
| `NacosConfigDiscoverer` | 自动发现辅助：读目标应用 Nacos 配置中 `spring.data.redis` / `spring.datasource.dynamic.datasource`，生成实例草稿（不含密码） |

### 3.2 采集域（collect/）

```java
public interface MetricCollector {                 // SPI
    InstanceType support();
    List<MetricPoint> collect(CollectorContext ctx);   // ctx 携带实例 DTO + ManagedConnection
}

public record MetricPoint(Long instanceId, MetricSource source, String metricName,
                          String node, Map<String, String> tags, double value, Instant ts) {}
```

| 类 | 要点 |
|----|------|
| `RedisMetricCollector` | INFO 分段解析（memory/stats/clients/persistence/replication）→ 指标点；cluster 模式逐节点 + `CLUSTER INFO`；命中率 = hits/(hits+misses) 由采集器算好 |
| `RedisSlowlogCollector` | `SLOWLOG GET 128`，命令参数脱敏（保留命令名+key 名，value→`***`），增量采集（记录上次 slowlog_id） |
| `BigKeyScanTask` | 独立低频任务（默认每日 02:30，可手动触发）：SCAN + `MEMORY USAGE`（<4.0 降级长度估算并标记 estimated）；Top-N 堆（N=500）；限速：每批 COUNT 1000、批间 sleep 50ms 可配；产出 report + items |
| `DbTypeAdapter` | `List<MetricPoint> collectInstanceMetrics(Connection)` / `List<SessionInfo> listSessions()` / `killSession(id)` / `List<SlowSqlRow> collectSlowSql()` / `List<CapacityRow> collectCapacity()`；实现 `PgAdapter`（pg_stat_activity/pg_stat_database/pg_stat_statements 若可用）、`MySqlAdapter`（performance_schema/global status）、`DmAdapter`（P1） |
| `DruidPoolCollector` | 当被监控应用同属本框架且可达时，优先取 Druid StatViewServlet 的 `/druid/datasource.json`（需运维侧开启并配白名单）；不可达时降级 DbTypeAdapter |
| `ServiceMetricCollector` | Nacos `NamingService.getAllInstances` → 并行 GET 各实例 actuator（`/actuator/health`、`/actuator/metrics/{name}`，走内网地址，网关外不经过鉴权链路，用 monitor 专用 header 或 IP 白名单）→ 聚合成指标点 |
| `MonitorClickHouseWriter` | 复刻 `ClickHouseBatchWriter`：双缓冲、`JSONEachRow`、循环重试、磁盘备份、Micrometer 指标（carlos.monitor.sink.*） |

### 3.3 Redis 数据管理代理（redis/proxy/）

| 类 | 要点 |
|----|------|
| `RedisDataProxy` | 类型化 API：`scan(instanceId, cursor, pattern, type, count)` / `keyDetail(key)` / `stringSet/hashPut/listOp/setOp/zsetOp/expire/persist/rename/delete/batchDelete`；所有 key 二进制安全编码（KeyCodec 统一 UTF-8 + 不可见字符转义） |
| `KeyScanner` | 游标式 SCAN 封装：单次接口调用最多推进 K 个 SCAN 批次（K 可配防长阻塞），返回 nextCursor；type 过滤在 SCAN 后批量 TYPE 管线化 |
| `RedisWriteGuard` | 写前置链：实例 manage_enabled → 命令白名单 → 高危操作校验 `X-Confirm-Token`（前端二次确认弹窗由后端签发的一次性 token，60s 有效，绑定 instanceId+操作摘要）→ 前值快照 |

### 3.4 SQL 安全与数据代理（db/proxy/）

| 类 | 要点 |
|----|------|
| `SqlGuard` | `GuardResult check(String sql, DbType, SqlMode mode)`；基于 Druid WallParser + WallVisitor：语句计数、语句类型白名单、WHERE 恒真检测（`OpUtils.isAlwaysTrue`）、函数/表黑名单（pg_catalog 写、xp_cmdshell 等）；严禁正则判断 SQL 类型 |
| `SqlFingerprintUtil` | Druid `SQLUtils.normalize` 归一化 → MurmurHash → 指纹；样例 SQL 参数占位化存储 |
| `DbDataProxy` | 元数据（information_schema 查询，按 DbTypeAdapter 方言）、表数据分页（强制 LIMIT/OFFSET 或 keyset）、受控执行（超时 statement_timeout 默认 10s 可配） |
| `DataMasker` | 规则匹配（全局规则 + 实例规则，实例规则优先）→ 结果集/map 结构按 mask_type 处理；规则 Caffeine 缓存 60s |

### 3.5 告警引擎（alarm/engine/）

| 类 | 要点 |
|----|------|
| `AlarmEngine` | 入口 `evaluate(List<MetricPoint>)`；单线程事件处理器内调用，无并发问题 |
| `RuleMatcher` | 规则索引：metric_source → rules（Caffeine 缓存 60s，规则变更广播失效） |
| `AlarmStateMachine` | FIRING → CONFIRMED → RECOVERED；FIRING 也可直接 RECOVERED；状态迁移全部走 Manager 层条件更新（`WHERE alarm_status = 期望值`）防并发覆盖 |
| `AlarmNotifier` | 组装文案模板（实例名/指标/阈值/当前值/级别/时间/大盘链接）→ message-api Feign 发送；失败重试 3 次后记 notify_status=FAILED |
| `SilenceChecker` | 查询生效中静默（rule_id + (instance_id 为空或等于当前) AND now between start/end） |

### 3.6 操作审计（audit/）

```java
@MonitorAudit(action = "REDIS_DATA_DELETE", target = "#instanceId", snapshot = true)
```

- `MonitorAuditAspect`：解析 SpEL 取实例与参数摘要，方法执行前抓前值快照（写操作），执行后组装事件 → `AuditMqLogStorage`（audit-api 提供的 MQ 埋点通道）异步上报；
- 审计内容：操作人（SecurityContext）、实例、action、命令/SQL 摘要、前值快照、结果、耗时、来源 IP；失败操作同样上报。

## 4. API 设计

统一前缀 `/monitor`，统一 `Result<T>` 响应、Param/DTO/VO 分层、MapStruct 转换、`@PreAuthorize` 权限点。下表为接口清单（详细出入参契约在 api 模块开发时以 Knife4j 注解固化）：

### 4.1 实例管理 MonitorInstanceController / MonitorGroupController

| 方法 | 路径 | 权限点 | 说明 |
|------|------|--------|------|
| GET | /monitor/instances/page | monitor:instance:view | 分页（类型/环境/分组/健康/关键字过滤） |
| GET | /monitor/instances/{id} | monitor:instance:view | 详情（password_cipher 不返回） |

## 7. 安全设计汇总

1. **认证授权**：全部接口过 gateway + 资源服务器；`@PreAuthorize("hasAuthority('monitor:xxx')")` 按钮级控制；实例级数据权限：非管理员角色需经 monitor_group_auth 校验（自定义 `MonitorDataScope` 切面，注入 SQL 查询条件，复用 datascope 思路）。
2. **凭据**：SM4 加密落库；仅存于连接注册中心内存，永不序列化出服务边界；前端不回显；日志脱敏（`Logback` 层面 password 关键词过滤 + 代码层禁止 toString 泄露）。
3. **高危操作**：confirm-token 一次性令牌（后端签发，Redis 存储，绑定操作摘要防篡改）+ 二次确认 + 全量审计；prod 环境实例的 sql_write_enabled 默认 false。
4. **注入防护**：Redis 无任意命令入口；SQL 经 WallParser 白名单；表数据浏览的排序/条件字段经白名单映射（防列名注入，对齐 OrderMapping 思想）；MyBatis 侧全部 `#{}`。
5. **采集安全**：采集命令集只读白名单；MONITOR 采样限时 10s 且仅管理员手动触发；被监控端连接池设小上限，监控端故障不传导。
6. **审计**：第 3.6 节埋点全覆盖写操作；monitor_sql_history 长期留档。

## 9. 部署与集成

1. **部署形态**：cloud 模式独立部署（默认端口建议 9518，待端口规划确认），经 gateway 路由 `/monitor/**`；boot 模式可并入单体。
2. **网络要求**：monitor 节点到各被监控实例（Redis/DB）、各微服务 actuator 内网地址、Nacos、ClickHouse 可达。
3. **初始化步骤**：① 执行 `monitor_postgresql.sql` 与 `monitor_ck.txt`；② 执行 `seed_monitor_dicts.sql`、`seed_monitor_operations.sql`；③ 菜单管理页登记「监控中心」目录与页面；④ job 中心确认采集 handler 注册；⑤ 配置 `carlos.monitor.*`（Nacos 配置中心）。
4. **对既有模块的改动**：零侵入——audit/message/job 仅通过既有 Feign/MQ 通道集成；被监控业务服务仅需开启 Druid stat（慢 SQL 场景）与 actuator 端点暴露。

## 10. 性能与容量设计要点

| 项 | 设计 |
|----|------|
| 采集吞吐 | Disruptor 6 万环 + 2000/批 × 3s flush ⇒ 约 6.7 万点/s 上限，远高于 1.7 万点/分需求（NFR-03 达标余量 >200 倍） |
| 查询 | 实时值走 Caffeine+Redis 二级缓存；时序按 range 自动路由原始/聚合表；CK 查询超时 5s |
| 连接资源 | 实例连接池惰性创建 + 30min 未访问驱逐；DB 池 maxActive=8，监控不对生产池造成压力 |
| 大实例保护 | SCAN 单次接口调用最多推进 K 批；表数据强制分页；SQL 超时 10s |
| 降级 | CK 不可用时指标落盘备份，页面实时值仍可用（Redis 缓存）；采集失败实例标记 DOWN 并跳过后续采集类型 |
