# DESIGN-20260925 MQ 技术选型

> **状态**：建议稿（2026-09-25 决策回填）。P-2 已决策为「**前期共用实例**」，P-1 状态存疑待核实，P-3 必须落实；第 6.2 节仍有 7 项未决。**§4.5 的缓解措施与拆分触发线是投产前置条件。**

## 1. 背景与目标

### 1.1 为什么现在要做这件事

框架内目前**没有已拍板的 MQ**。存在一个名为 `carlos-spring-boot-starter-mq` 的多 MQ 抽象模块，但它既未投产、也不完整（见 1.3.1）。与此同时，框架内已出现多个**明确需要消息机制**的扇出点，它们现在靠同步 Feign 或进程内事件硬扛（见 1.3.3）。

本文档的目标是：在既有约束下选定一个可落地的 MQ 方案，并明确其能力边界与前置条件。

### 1.2 选型约束（决策者给定）

| # | 约束 | 对选型的影响 |
|---|---|---|
| C1 | 使用场景**四个全要**：业务事件解耦、异步任务卸载、延迟/定时任务、事务最终一致性 | 需要延迟消息能力与可靠投递 |
| C2 | **单机/双机自建，无专职运维** | **强烈偏好部署组件少、无独立中间件的方案** |
| C3 | **兼容性优先**：只要能在 Spring Boot 4.0.6 上稳定跑，砍功能可接受 | 排除无 Boot 4 官方支持的客户端 |
| C4 | 倾向国产但**非硬性** | 不构成硬约束（见 3.2.6） |

框架基线：Spring Boot 4.0.6 / Spring Cloud 2025.1.1 / SCA 2025.1.0.0 / JDK 21。

### 1.3 现状盘点

#### 1.3.1 已有 MQ 抽象是半成品

`carlos-spring-boot-starter-mq` 处于「设计文档齐全、发送勉强可通、**消费从未实现**」的状态：

| 问题 | 证据 |
|---|---|
| **消费链路从未实现** | 三个 client 的 `subscribe()` 均只把 listener 塞进 map，无任何消费者注册。`client/rocketmq/RocketMqClient.java:186-190` 同理 kafka/rabbitmq |
| **`@MqListener` 无任何处理器** | 全模块 grep `BeanPostProcessor\|ImportBeanDefinitionRegistrar\|SmartInitializingSingleton` **零匹配**；`DEVELOPMENT_PLAN.md` 中打勾的 `MqListenerAnnotationBeanPostProcessor`、各 `*ListenerAdapter`、`MqMessageBuilder`、`MqMetricsCollector` 等文件**全部不存在** |
| **`KafkaMqClient` 在 Boot 4 上必然失效** | `client/kafka/KafkaMqClient.java:120-121,292` 反射调用 `org.springframework.util.concurrent.{SuccessCallback,FailureCallback,ListenableFutureCallback}`，这些类 **Spring Framework 6 已删除** ⇒ `sendAsync` 恒走 catch 分支 |
| **事务消息是假的** | `client/rabbitmq/RabbitMqClient.java:252-254` 直接 `return send(message); // RabbitMQ 事务简化实现` |
| **能力矩阵与实际不符** | `pom.xml:22-24` 把 RocketMQ 作为**硬依赖**、`:25-29` 把 Kafka 标为 `provided`、**完全没有 amqp 依赖** ⇒ 所谓「三选一自动检测」实际**永远解析成 ROCKETMQ**，RabbitMQ 分支不可达 |
| **零测试、零使用者** | `src/test` 目录不存在；全仓库除样例 `carlos-samples/carlos-sample-mq` 外无任何引用 |

结论：**该模块不能作为选型的基础假设**，只能作为改造对象。

#### 1.3.2 事实上的 MQ：carlos-message 的 Redis Stream 队列

框架内**真正在生产运行**的消息能力不在上述 starter 里，而在消息中心：

- 接口：`carlos-integration/carlos-message/carlos-message-core/.../core/queue/MessageQueue.java`
- 实现：`carlos-integration/carlos-message/carlos-message-bus/.../queue/RedisStreamMessageQueue.java:53`
- 机制：**即时消息**走 Redis Stream + Consumer Group（`StringRedisTemplate.opsForStream()`）；**延时/定时消息**走 Redisson `RDelayedQueue`（`:69-92`，三级优先级，daemon 转移线程，零轮询）
- 它是**绕开** `carlos-spring-boot-starter-mq` 独立实现的

**这是本选型最重要的既有资产**：一个已验证可行、零新中间件的实现范本。

#### 1.3.3 真实的 MQ 候选消费点

以下位置当前用同步 Feign 或进程内事件实现，是 MQ 的天然接管对象：

**A. 审计日志扇出（信号最强）**——全部在**登录热路径**上，且是 fire-and-forget：

| 位置 | 说明 |
|---|---|
| `carlos-auth/.../oauth2/handler/Oauth2LogoutSuccessEventHandler.java:117` | 登出后同步 Feign 写审计 |
| `carlos-auth/.../security/handle/CustomAuthenticationSuccessHandler.java:91` | 登录成功 |
| `carlos-auth/.../security/handle/CustomAuthenticationFailureHandler.java:89` | 登录失败 |
| `carlos-auth/.../security/handle/FormLoginSuccessHandler.java:71` / `FormLoginFailureHandler.java:64` | 表单登录 |
| `carlos-auth/.../session/service/OnlineUserService.java:162` | 在线用户操作 |
| `carlos-auth/.../audit/service/SecurityAlertService.java:377` | 安全告警 |
| `carlos-auth/.../log/LoginAuditLogSender.java:34-43` | **已被包成 `@Async("virtualTaskExecutor")` + try/catch 的"伪异步" Feign**——语义上最接近 MQ 的一处，但退化成线程池 + 无重试无持久化 |
| `carlos-agent/.../service/AgentChatService.java:96` | AI 对话落审计 |

被调方 `carlos-audit-bus/.../clickhouse/ClickHouseBatchWriter.java` 用 `ConcurrentLinkedQueue` + 双缓冲在进程内批量落 ClickHouse——**即"进程内队列 + HTTP 同步入口"硬凑的准 MQ**。

**B. 进程内事件（多实例即失效）**

- 网关限流告警与指标：`carlos-gateway/.../ratelimit/CarlosRedisRateLimiter.java:42,201` 发布 → `ratelimit/event/RateLimitExceededEvent.java:19`、`RateLimitMetricsEvent.java:18` → `ratelimit/listener/RateLimitAlertListener.java:48` 监听。**多实例网关下无法聚合**。
- `carlos-system/.../config/SystemEventListener.java:22-26` 监听 `ApplicationReadyEvent` 但**方法体为空**（预留未实现）。

**C. 缓存失效需跨实例广播**

- `carlos-org-bus/.../manager/impl/OrgDepartmentManagerImpl.java:422-472`：手工维护 `dept:hash:{id}` / `dept:children:{parentId}` / 祖先链 / 子孙集合**共 7 类 key**——一套手写的一致性协议。
- `carlos-system-bus/.../region/controller/SysRegionController.java:171-183`、`.../dict/controller/SysDictController.java:104-109`：**缓存刷新靠人工调 HTTP 接口**，多实例要逐个打。
- `carlos-system-bus/.../configration/service/SysConfigService.java:146-147`：Caffeine 本地静态缓存（30min），**多实例间无法一致**。（此条**部分已被现有能力覆盖**，见 1.3.4——但覆盖范围仅限走 Redisson 的缓存。）

#### 1.3.4 carlos-spring-boot-redis 的 MQ 能力审计

**结论：该模块对 MQ 的支持为零——不是不完善，而是完全不含。**

模块职责仅限：缓存（Caffeine / 两级缓存）、分布式锁、限流、Lua、序列化、指标、健康检查。**65 个源文件中无任何 queue / topic / stream / pubsub / mq 包。**

全仓 grep 结果：

| API | 全仓命中 | 位置 |
|---|---|---|
| `RTopic` / `RReliableTopic` / `RStream` / `RQueue` / `StreamMessageListenerContainer` | **0** | — |
| `RDelayedQueue` / `RBlockingQueue` | 11 + 6 | **全部在 `carlos-message/.../queue/RedisStreamMessageQueue.java` 单个文件内** |
| `opsForStream` | 5 | 同上 |
| `convertAndSend`（发布订阅） | 10 | 9 处为 WebSocket；`carlos-spring-boot-redis` 中仅 **1 处** |

`RedisUtil`（2920 行 / 162 个静态方法）的 MQ 相关能力只有一个方法：`RedisUtil.java:2909-2911` 的 `convertAndSend(channel, message)`——**只有发布，没有订阅**。而 `redisTemplate.opsForZSet()` / `opsForList()`（`:90-91`）仅暴露 ZSET/LIST 原语，**无 Stream**。

**但底座具备**——能力在 Redisson 里，不在框架里：

1. `RedissonClient` bean 可用（由 `redisson-spring-boot-starter` 提供，`RedissonConfig.java:50` 仅用它构建 `RedissonConnectionFactory`）⇒ 任何模块都可直接调用 Redisson 的 MQ API。**这正是 `carlos-message` 能做到而其他模块没做的原因。**
2. `RedissonLocalCacheManager.java:15,48` 的 `RLocalCachedMap` + `SyncStrategy.INVALIDATE` **已内建跨实例缓存失效**（Redisson 内部以 Pub/Sub 同步）⇒ 1.3.3-C 中「Caffeine 本地缓存无跨实例失效」一条**在走 Redisson 的缓存上已被覆盖**；但原生 Caffeine（`SysConfigService.java:146-147`）不在覆盖范围内。

**对落地的影响**：框架侧**没有任何 MQ 底座可复用**，实施属「从 0 建能力」而非「接线」（见 5.2）。

### 1.4 既有选型先例

`docs/design/DESIGN-20260922-基础框架能力补齐计划.md:79-85` 中 S1 定时任务的选型结论：

## 2. 兼容性硬约束（决定性）

### 2.1 Boot 4.0.6 BOM 实证

读取本地 `spring-boot-dependencies-4.0.6.pom` 得到权威版本矩阵：

| 客户端 | Boot 4.0.6 管理版本 | 官方支持 |
|---|---|---|
| `spring-amqp`（RabbitMQ） | **4.0.3** | ✅ 一等公民 |
| `spring-kafka` | **4.0.5** | ✅ 一等公民 |
| `spring-pulsar` | **2.0.5** | ✅ 一等公民 |
| **RocketMQ** | **无任何条目** | ❌ 不在 Spring 管理范围 |

配套：`kafka-clients 4.1.2`、`rabbit-amqp-client 5.27.1`、`pulsar-client 4.1.3`。Boot 4 已按技术拆分出独立 starter（`spring-boot-starter-kafka` / `-amqp` / `-pulsar`）。

### 2.2 由此得到的边界

- Kafka / RabbitMQ / Pulsar 三家的 Spring 集成在 Boot 4 上**均为一等公民**，无兼容性顾虑。
- RocketMQ **不能**简单断言为「不兼容」——SCA 2025.1.0.0（本项目正在用）已通过 **Spring Cloud Stream binder** 将其适配到 Boot 4（详见 3.2.4）。其排除理由不是兼容性，而是运维成本。
- **所有 Spring 生态 starter 都绑死在 Framework 内部实现上**，这是 Boot 4 升级中的主要风险来源（1.3.1 中 `KafkaMqClient` 的死法即为此类）。纯客户端库（如 Redisson）不存在该风险。

## 3. 候选评估

### 3.1 对比矩阵

| 维度 | RabbitMQ | Kafka | Pulsar | RocketMQ | **Redis Streams** |
|---|---|---|---|---|---|
| Boot 4 官方支持 | ✅ | ✅ | ✅ | ⚠️ 需自担适配 | ✅ 纯客户端 |
| 业务事件解耦 | ✅ | 🔶 需按事件建 topic | ✅ | ✅ | ✅ |
| 异步任务卸载 | ✅ | ✅ | ✅ | ✅ | ✅ |
| **延迟/定时消息** | 🔶 需插件 | ❌ **无原生** | ✅ | ✅ 原生 | ✅ `RDelayedQueue` |
| 事务最终一致性 | 🔶 走 outbox | 🔶 走 outbox | 🔶 走 outbox | ✅ 原生事务消息 | 🔶 走 outbox |
| **单机/双机自建、无专职运维** | 🔶 Erlang ≥27 硬门槛 | ❌ KRaft 运维面大 | ❌ 组件最多 | ❌ NameServer+Broker(+Proxy) | ✅ **零新中间件** |
| 管理 UI / 消息追踪 | ✅ 最好 | 🔶 需外部工具 | 🔶 | ✅ | 🔶 需自建 |
| 死信/重试/积压监控 | ✅ 内置 | 🔶 需配 DLT | 🔶 | ✅ | ❌ **需自建** |

### 3.2 逐候选结论

#### 3.2.1 RabbitMQ —— ❌ 不作为 P0

- 优点：Boot 4 一等公民（`spring-amqp 4.0.3`）；单容器即可起步；管理 UI 与 DLX/重试/积压监控内置，对无专职运维团队价值最高的恰恰是这些。
- 排除理由：**4.3.6 要求 Erlang ≥ 27.0，官方明确「版本不匹配节点直接起不来」**——在无专职运维的前提下，养一个 Erlang 运行时是持续负担。
- 附加坑：**4.x 已弃用 classic mirrored queue**，双机 HA 变得尴尬（quorum queue 期望奇数节点），与 C2 的「双机」不匹配。

#### 3.2.2 Kafka —— ❌ 出局

- **无原生延迟消息**，不满足 C1 中的「延迟/定时任务」；用外部调度模拟延迟消息属自找麻烦。
- 4.0 起 **ZooKeeper 彻底移除、只有 KRaft，且迁移不可逆**，运维面比 3.x 换了一套新账，与 C2 冲突。
- 定位错配：Kafka 擅长高吞吐日志流与重放，而本项目当前需求是事件解耦与任务卸载，不是流处理。

#### 3.2.3 Pulsar —— ❌ 出局

组件最多（broker + bookkeeper + metadata store，存储计算分离），与 C2 正面冲突。

#### 3.2.4 RocketMQ —— ❌ 不作为 P0（但**保留为回流选项**）

- **能力面最贴合 C1**：原生延迟消息、事务消息、顺序消息、消息轨迹，四个场景全覆盖。
- **兼容性并非死结**（此处更正一种常见误判）：
  - SCA 2025.1.0.0 release notes 含 `[RocketMQ]: RocketMQ module support Spring Boot 4.0 (#4216)`，其 `spring-cloud-starter-stream-rocketmq-2025.1.0.0.pom` 依赖 `spring-cloud-stream 5.0.0` + `rocketmq-client 5.3.1`，**是实打实的 Boot 4 制品**；
  - 官方 `rocketmq-spring-boot-starter` 最新 2.3.6 虽仍以 Boot 2.7 构建，但其引用的 **62 个 Spring 类在 Boot 4 中全部存在**，唯一真障碍是硬引 Jackson 2（Boot 4 默认仅 Jackson 3），补 `jackson-databind 2.x` 或 `spring-boot-jackson2` 即可。
- **排除理由 = C2（运维成本）**：需 NameServer + Broker(+Proxy)；官方对「单机单副本」明确标注「风险高、不建议线上」。
- 附带不利事实：SCA 的路径走 **Spring Cloud Stream binder 模型**，与现有 `MqTemplate` 抽象是两套编程模型；且 **Seata 仅支持 RocketMQ 且仅用于事务消息，其自身 Boot 4 支持仍在 RC 阶段**（Central 上仅 2.6.0，SCA 需为其打 workaround #4245）。

#### 3.2.5 Redis Streams（Redisson / spring-data-redis）—— ✅ **选用为 P0**

- **零新中间件**，直接延续 1.4 的选型先例。
- **Boot 4 风险已被经验证，而非结构上为零**：框架实际引入的是**第三方 starter** `redisson-spring-boot-starter`（见 `carlos-spring-boot-starter-redis/pom.xml`），风险点正是在它身上，**不能宣称「结构上不可能坏」**。但 Redisson 4.5.0 已在 Boot 4.0.6 上**实际运行**（缓存/锁/限流均在用）⇒ 属「**经验证成立**」。含义：将来升级 Boot 时，Redisson starter 需与框架自身一同纳入验证清单。
- **能力面覆盖 C1**：Redis Stream 有真正的 Consumer Group + `XACK`/`XPENDING`/`XCLAIM`（at-least-once）；`RDelayedQueue` 提供**任意精度的延迟消息**（优于 RabbitMQ 的插件方案与 Kafka 的缺失）；`RTopic`/`RReliableTopic` 覆盖广播失效场景。
- **已有生产验证的参考实现**（1.3.2），落地是「抽取」而非「新建」。
- **注意**：`spring-cloud-stream-binder-redis` 已停更在 `1.0.0.RELEASE`（废弃），因此**必须使用 `spring-data-redis` 原生 API，不得引入 Spring Cloud Stream**。这与 1.3.2 现有实现的做法一致。

#### 3.2.6 其他候选

- **NATS**：`nats-spring` 仅到 Boot 3.5，无 Boot 4 版本 ⇒ 出局。
- **信创 MQ（东方通 TongLINK/Q、宝兰德、金蝶 Apusic）**：在 Maven Central **查不到任何 artifact**；是否提供 `jakarta.jms`（Boot 4 只认 Jakarta，不认 `javax.jms`）**无法证实**。⇒ C4 目前**无法落地**，不作为选型依据。

## 4. 选型结论

### 4.1 结论

**选用 Redis Streams（`spring-data-redis` + Redisson）作为框架 P0 的默认 MQ 实现。**

定位：以最小运维成本满足 C1/C2/C3，落地路径为「把 1.3.2 的既有实现抽取为框架级能力」。抽象层保留可插拔能力，为第 7 节的回流留出位置。

### 4.2 三项前置条件（2026-09-25 决策回填）

| # | 前置条件 | 决策 / 实测 | 结论 |
|---|---|---|---|
| **P-1** | **AOF 开启** | 决策者答复「已开启」；但本次可连通实例两次实测（间隔约 1 小时）均为 `aof_enabled=0` | ⚠️ **待核实**（见下） |
| **P-2** | **独立 Redis 实例**，不与缓存/token 共用 | **前期主动放弃**——接受共用 | ⚠️ **风险自担，且 4.5 的缓解措施由「建议」转为「必须」** |
| **P-3** | **设 `maxmemory` 且保持 `noeviction`** | 实测 `maxmemory=0`（无上限） | ❌ **必须设置** |

**P-1 的核实要点**：报「已开启」的实例与本次实测实例**很可能不是同一个**。证据——该实例 `uptime_in_days=38`，即 38 天内未重启；而 `appendonly yes` 生效需重启或 `CONFIG SET appendonly yes`，故该实例的 AOF **不可能**在近期被开启过。请确认生产实例状态，并**消除 dev/prod 配置漂移**：若仅生产开 AOF，则**本地测试无法暴露持久性差异**。

**P-2 是本方案唯一无法靠配置绕过的结构性风险**：框架 **token 全量落 Redis**（S4 有状态 token + `oauth2:session_meta:{authId}`）。共用实例下，一次消息积压即可打到认证链路上。既然前期选择共用，则 4.5 的措施与触发线是投产的前置条件，而非可选项。

> 一个仍然成立的好消息：`maxmemory_policy` 实测为 `noeviction`，不会**静默淘汰**消息。风险在于「无上限导致 OOM」与「写满后所有写入失败」，而非「淘汰丢消息」。

### 4.3 场景边界：明确不做什么

即便 P-1~P-3 全部满足，也不应把所有流量压给 Redis：

| C1 场景 | 是否交给 Redis Streams | 说明 |
|---|---|---|
| 业务事件解耦（缓存失效广播、组织/角色变更通知） | ✅ **最适合** | 丢失可容忍、可重放 |
| 异步任务卸载（短信/邮件） | ✅ **仅限 P-1 满足后** | 丢一条短信即一次业务失败 |
| **延迟/定时任务** | ❌ **归 carlos-job（Quartz）** | 已交付，`JobScheduleTypeEnum.java:22-24` 含 `ONCE(3,"一次性触发")` |
| **事务最终一致性** | ❌ **不直接压给 MQ** | 走 **PG 本地消息表（outbox）+ 重试**，MQ 仅做投递加速 |

后两条为**设计决策而非妥协**：延迟调度已由 Quartz 覆盖，无需为它引入 MQ 能力；而「最终一致性靠 outbox」对 RabbitMQ / Kafka / RocketMQ 同样成立（RabbitMQ 无跨库事务消息、Kafka 事务仅限 Kafka 内部），因此该边界**不构成对 Redis 方案的歧视**。

### 4.4 目标形态

```
业务模块
   │  仅依赖 MqTemplate（传输中立）
   ▼
carlos-spring-boot-starter-mq
   ├── core:  MqTemplate / MqMessage / ConsumeResult（能力用 capability 声明）
   ├── client/redis:  RedisStreamMqClient（抽取自 carlos-message）  ◀── P0 默认
   └── client/{rabbitmq,kafka,rocketmq}: 保留 SPI 位，暂不实现
   │
   ▼
Redis（**前期与缓存/token 共用**，AOF 待核实，需设 maxmemory + noeviction，**消息量必须有界**）
```

### 4.5 共用实例：缓解措施与拆分触发线

因前期接受 P-2 风险，下列措施**由「建议」转为「必须」**。

#### 必须落实的缓解措施

| # | 措施 | 作用 | 落点 |
|---|---|---|---|
| **M1** | **插入即修剪**：`XADD key MAXLEN ~ N`；延时队列设最长期限与总量上限 | **把"无界积压"变成"固定预算"——这是让共用变得可承受的最关键一条** | 代码（`client/redis`） |
| **M2** | **显式设 `maxmemory`**（留足余量），保持 `noeviction`，并在 **80% 处告警** | 当前 `maxmemory=0`，进程可涨到被 OOM-kill；且本实例 `process_supervised=no`，**被杀了没有守护进程自动拉起** | 运维 |
| **M3** | **逻辑 DB 隔离**（消息用独立 DB） | **仅隔离 keyspace（限制 `FLUSHDB` 爆炸半径），不隔离内存/淘汰/持久化**。本实例已在用 db0/db1/db5，成本极低 | 运维 + 配置 |
| **M4** | **生产者侧背压/降级**：Stream 长度超阈值即可容忍流量降级丢弃、不可容忍流量快速失败 | 防积压无限增长。可复用 `NoOpMqTemplate` 的降级思路 | 代码 |
| **M5** | **前期只承接可容忍丢失的流量**（审计日志试点）；**短信/邮件暂不上** | 内存耗尽的失败模式会同时打到认证与消息两条链路 | 实施顺序 |
| **M6** | 监控 `used_memory` / Stream 长度 / PENDING 数 | 拆分触发线依赖这些指标 | 运维 |

#### 必须知道的三个耦合机制

1. **单线程**：本实例 `io_threads_active=0`。`XRANGE` / `XTRIM` / `XPENDING` 在大 Stream 上是 **O(N)** 且阻塞整个实例——**会直接表现为登录延迟尖刺**。
2. **淘汰策略是全局唯一的**：Redis 只有**一个** `maxmemory-policy`，无法做到「缓存 LRU 淘汰」与「消息绝不淘汰」并存。当前 `noeviction` 意味着**缓存同样无法淘汰**，两边增长共用同一个天花板。
3. **内存写满的后果是「全部写入失败」而非「淘汰一部分」**：`noeviction` 下触达 `maxmemory` 后所有写命令报错——**包括 token/session 写入，即全站登录失败**。这是共用方案最尖锐的风险。

#### 拆分触发线（命中任一即必须拆出独立实例）

1. 消息类键的内存占用 > `used_memory` 的 **20%**
2. Stream 长度 / PENDING 数**持续增长**（M1 失效）
3. `used_memory` 触及 `maxmemory` 的 **70%**
4. **需要给缓存配 LRU/淘汰策略时**——与消息的 `noeviction` 需求正面冲突，此时不拆无解
5. 需要承接**不可丢**流量（短信/邮件）时
6. 认证链路 P99 延迟出现与消息量相关的抖动

#### 关于 Cluster 模式

本次可连通实例为 **Redis 8.4.0 `standalone`，`cluster_enabled=0`**（宝塔面板托管）。生产需自行确认：

```bash
redis-cli -h <host> -p <port> INFO cluster     # cluster_enabled: 0/1
```

若生产为 **Cluster 模式**，有两个后果须提前验证：

- **M3 失效**——Cluster 仅支持 db0，无法用逻辑 DB 做隔离。
- **Redisson `RDelayedQueue` / `RBlockingQueue` 与 Stream 操作安全性不同**：后者是单键操作、天然 cluster 安全；前者涉及多键与 Lua，**存在跨 slot 约束**，须实测（见 6.2）。

## 5. 落地方案

### 5.1 抽象层改造

现有 `MqTemplate` 是**按 RocketMQ 特性设计的**（含 `sendTransaction`），与目标实现不匹配，需重塑：

1. **去除传输特有方法**：`sendTransaction` 移出核心接口（保留为 RocketMQ 专属扩展点）。
2. **能力声明化**：延迟/顺序/事务等按 capability 标志暴露，不支持的能力**显式报错**而非静默降级（现有 `NoOpMqTemplate` 的降级方式值得保留）。
3. **补齐消费端**：实现 `@MqListener` 的 `BeanPostProcessor` 与消费者注册——**这是当前最大的缺口**，消费链路需从零实现。
4. **清理错误默认**：修正 `pom.xml:22-24` 的 RocketMQ 硬依赖，改为所有实现均 `provided`/`optional`；修正「auto 检测实际恒为 ROCKETMQ」的误导行为。
5. **修掉死代码**：`KafkaMqClient` 的 `org.springframework.util.concurrent.*` 反射、`MqClientSelector` 与 `OnMqTypeCondition` 两套不一致的探测逻辑、`MqAutoConfiguration` 的自引用环与缺失的 `matchIfMissing`。

### 5.2 实现来源：抽取而非重写，但属「从 0 建能力」

以 `carlos-integration/carlos-message/carlos-message-bus/.../queue/RedisStreamMessageQueue.java` 为蓝本抽取到 `client/redis`，保留其两个关键设计：

- 即时消息用 `StreamOperations` + Consumer Group（含 `XACK`、PENDING 认领）
- 延时消息用 Redisson `RDelayedQueue` 三级优先级 + daemon 转移线程

**定性说明**：1.3.4 已证实 `carlos-spring-boot-redis` **不含任何 MQ 能力**，因此这是**从 0 建框架级能力**，不是「接线」。`RedisUtil` 亦缺订阅侧原语与 Stream 支持，需补。

#### 模块归属

| 方案 | 评价 |
|---|---|
| 放进 `carlos-spring-boot-redis` | ❌ 它是缓存模块；会让每个只想用缓存的服务在 classpath 上背上 broker 语义 |
| **放进 `carlos-spring-boot-starter-mq` 的 `client/redis`** | ✅ 推荐。该 starter 当前**不含 redis 依赖**，需为其新增一个 **optional** 的 `carlos-spring-boot-starter-redis` |

#### 需从零实现清单（现有实现与框架均未覆盖）

| 项 | 说明 |
|---|---|
| 消费端 `BeanPostProcessor` + `@MqListener` 处理器 | 当前完全不存在（见 1.3.1） |
| 死信队列 | Redis 无内置 DLQ |
| 重试计数 | 需基于 PENDING / 投递次数自行实现 |
| 积压指标 | 需基于 `XLEN` / `XPENDING` 采集 |
| Stream 修剪（`XTRIM`）策略 | 不配置则 Stream 无限增长 |
| `RedisUtil` 的 Stream 与订阅侧原语 | 现有仅一个发布方法 |

以上均为 **RabbitMQ 免费提供而 Redis 需自建**的部分，是本方案的固有成本。

### 5.3 试点：审计日志扇出（P0）

**理由**：位于登录热路径、fire-and-forget 语义、丢失可容忍且可重放——收益最大、风险最小。

改造点（1.3.3-A）：`Oauth2LogoutSuccessEventHandler.java:117`、`CustomAuthenticationSuccessHandler.java:91`、`CustomAuthenticationFailureHandler.java:89`、`FormLoginSuccessHandler.java:71`、`FormLoginFailureHandler.java:64`、`OnlineUserService.java:162`、`SecurityAlertService.java:377`、`AgentChatService.java:96`。

其中 `LoginAuditLogSender.java:34-43` 已是 `@Async` 伪异步形态，**可直接替换为 MQ 投递**，是最省力的起点。

## 6. 风险与未决项

### 6.1 风险

| 级别 | 风险 | 缓解 |
|---|---|---|
| **高** | broker 与缓存/token 共用实例 ⇒ 积压打到认证链路（**2026-09-25 已决策接受**） | 4.5 的 **M1–M6 必须落实** + 6 条拆分触发线 |
| **高** | `noeviction` + 内存写满 ⇒ **所有写入失败，含 token ⇒ 全站登录失败** | M2 显式设 `maxmemory` 并在 80% 告警 |
| **高** | `maxmemory=0`（无上限）+ `process_supervised=no` ⇒ OOM 后**无守护进程自动拉起** | M2；并请运维确认 supervision 配置 |
| **中** | Redis 单线程：大 Stream 上 `XRANGE`/`XTRIM`/`XPENDING` 为 O(N) 且阻塞全实例 ⇒ 登录延迟尖刺 | M1 有界化 + M6 监控 |
| **中** | 淘汰策略全局唯一 ⇒ 无法同时满足「缓存淘汰」与「消息不淘汰」 | 触发线 4；冲突出现即拆 |
| **中** | **AOF 状态存疑**（自述已开 vs 实测 `aof_enabled=0`）⇒ dev/prod 配置漂移，**本地测试测不出持久性差异** | 4.2 核实要点 |
| 中 | 死信/重试/积压监控需自建 | 5.2 已列为必做项，不可省 |
| 中 | `XTRIM` 未配置 ⇒ Stream 无限增长 | M1 强制 + 代码评审检查项 |
| 低 | Cluster 模式下 Redisson `RDelayedQueue`/`RBlockingQueue` 的跨 slot 语义 | 见 4.5 末与 6.2 |

### 6.2 未决项（需确认或实测）

1. **AOF 状态核实（P-1）**：决策者答复「已开启」，但本次可连通实例两次实测均为 `aof_enabled=0`，且其 `uptime_in_days=38` 表明近期未重启 ⇒ **二者很可能不是同一实例**。需确认生产实例，并消除配置漂移。
2. **`maxmemory` 必须显式设置（P-3）**：当前 `maxmemory=0`。需确认取值，以及 4.5-M2 的 80% 告警是否已具备。
3. **生产 Redis 的 supervision 状态**：本实例 `process_supervised=no`，OOM 后无自动拉起；生产待确认。
4. **生产是否运行在 Redis Cluster 模式**：本次可连通实例为 `standalone`（`cluster_enabled=0`）；生产待确认。若为 Cluster，则 4.5-M3（逻辑 DB 隔离）失效，且 Redisson `RDelayedQueue` 的跨 slot 行为需实测。
5. **`RDelayedQueue` 的失效行为**：其转移依赖 Redisson 定时任务，**所有实例同时宕机时到期消息是否补发**需实测确认（可与 Cluster 模式一并验证）。
6. **RabbitMQ 4.3.x ↔ `amqp-client 5.27.1` 官方兼容矩阵**：未查到明确对照表（若走回流路径需确认）。
7. **RocketMQ 在 Boot 4 上的端到端可用性**：调研仅证明「无 Spring API 缺失 + 需补 Jackson 2」，**未做真实启动验证**。若走回流路径，须先在 `carlos-spring-boot-starter-mq` 上跑最小用例。

**已闭合（2026-09-25）**：P-2「是否与缓存/token 共用实例」——决策为**前期共用**，风险转为须落实 4.5 的缓解措施与拆分触发线。

## 7. 回流预案（何时改用独立 MQ）

抽象层保留 SPI 位，出现以下**任一信号**时评估回流，业务代码无需改动：

| 信号 | 倾向方案 |
|---|---|
| 需要给人看的管理 UI / 消息轨迹 | RabbitMQ |
| 需要复杂 topic 通配路由 | RabbitMQ |
| 单实例吞吐上到万级 / 出现大 backlog | Kafka 或 RocketMQ |
| 出现「消息绝不可丢」的合规要求 | RocketMQ（信创倾向）或 RabbitMQ |
| 信创转为硬性要求 | RocketMQ（**但须先解决 jakarta.jms 与 Boot 4 适配验证**，见 3.2.6 / 6.2-6） |
| 有了专职运维 | 重新评估全部候选 |
