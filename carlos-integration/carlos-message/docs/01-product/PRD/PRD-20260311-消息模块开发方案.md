## 一、需求确认摘要

### 1.1 业务需求

| 维度        | 确认内容                                    |
|-----------|-----------------------------------------|
| **消息场景**  | 任务通知(最高优)、验证码/系统通知(次高)、审批提醒(普通)、营销推送(低) |
| **时效性**   | 验证码10s、任务通知30s、审批1min、营销可延时             |
| **消息有效期** | 发送失败1小时后放弃                              |
| **发送量**   | 日均20万、峰值1000 QPS、高峰期6小时                 |
| **用户规模**  | 50万总用户、5万日活、1万WebSocket并发               |

### 1.2 渠道需求

| 渠道      | 优先级 | 特性                                        |
|---------|-----|-------------------------------------------|
| **短信**  | P0  | 多服务商切换（复用 carlos-spring-boot-starter-sms） |
| **钉钉**  | P0  | 工作通知、Markdown 消息                          |
| **站内信** | P0  | WebSocket 实时推送、已读回执、撤回指令                  |
| **邮件**  | P1  | SMTP/HTML 邮件发送                            |

### 1.3 技术约束

```
部署：单机开发 + K8s多实例(生产)
框架：Spring Cloud + Nacos
数据库：MySQL 8.0（消息独立库）
缓存：Redis（使用 carlos-spring-boot-starter-redis）
队列：Redis Stream + ZSet
定时任务：Spring @Scheduled
监控：Micrometer + Prometheus
```

### 2.2 核心流程设计

#### 消息发送流程

```
+-------------+    +-------------+    +-------------+    +-------------+
| 接收请求   |--> | 参数校验   |--> | 模板渲染   |--> | 敏感词过滤 |
|            |    |            |    | ${var}替换  |    | DFA检测    |
+-------------+    +-------------+    +-------------+    +------+------+
                                                                |
+-------------+    +-------------+    +-------------+    +------+------+
| 记录状态   |<-- | 执行发送   |<-- | 渠道适配   |<-- | 限流检查   |
| (成功/失败)|    |            |    |            |    | 滑动窗口   |
+-------------+    +-------------+    +-------------+    +-------------+
      |
+-----+-----+
|           |
+--------+ +--------+
| 成功   | | 失败   |
| 返回   | | 重试   |
+--------+ | 告警   |
           +--------+
```

#### 消息消费流程（Redis Stream）

```
+-----------------+    +-----------------+    +-----------------+
| Redis Stream   |--> | Consumer Group |--> | 限流检查       |
| (pending列表)  |     | (消费者组)     |     | (令牌桶算法)   |
+-----------------+    +-----------------+    +--------+--------+
                                                       |
                              +------------------------+
                              |                        |
                       +-------------+         +-------------+
                       | 限流通过   |         | 限流拒绝   |
                       | 渠道路由   |         | 延迟重试   |
                       +------+------+         +-------------+
                              |
                       +------+------+
                       |             |
                +----------+  +----------+
                | 发送成功 |  | 发送失败 |
                | ACK确认  |  | 重试计数 |
                +----------+  | >3次？   |
                              +----+-----+
                                   |
                        +----------+----------+
                        |                     |
                 +------------+      +------------+
                 | 重试<3次   |      | 进入死信  |
                 | 放回队列   |      | 告警通知  |
                 +------------+      +------------+
```

                                |
                     +---------------------+

## 六、关键设计决策

### 6.1 为什么使用 Redis Stream 而非 RabbitMQ/RocketMQ？

| 对比项       | Redis Stream | RabbitMQ | RocketMQ |
|-----------|--------------|----------|----------|
| **部署成本**  | 低（已有Redis）   | 中（需额外部署） | 高（需集群）   |

### 6.2 短信渠道多服务商设计

// 策略：权重随机 + 故障转移
public class ChannelRouter {
    public SendResult sendWithFallback(MessageContext context, ChannelType channelType) {
        List<ChannelAdapter> candidates = ChannelFactory.getChannelsByType(channelType)
            .filter(a -> a.isAvailable() && a.supports(context.getMessageType()))
            .sorted((a1, a2) -> Integer.compare(getWeight(a2), getWeight(a1)))
            .collect(Collectors.toList());

        for (ChannelAdapter adapter : candidates) {
            SendResult result = adapter.send(context);
            if (result.isSuccess()) return result;
        }
        return SendResult.fail("ALL_CHANNELS_FAILED");
    }
}
