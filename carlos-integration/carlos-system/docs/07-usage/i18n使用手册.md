## 1. 功能概述

Carlos Framework i18n 模块提供一套前后端协作的国际化方案，核心是**把「翻译」和「运营覆盖」两件事分开**：

- **前端语言文件 = 完整的 key 目录 + 基线值**，同时是 `$t()` 的类型来源与离线兜底
- **后端数据库 = 只存运营改过的那些 key 的覆盖值**
- **运行时合并**：`$t(key)` 拿到的值 = 后端覆盖值 ?? 前端基线值

因此既保留了编译期类型安全与离线可用，又支持运营不发版改文案。

### 核心特性

| 特性      | 说明                                                     |
|---------|--------------------------------------------------------|
| 前端目录为源  | key 目录与基线值在 `locales/langs/*.ts`，也是 `$t()` 的类型来源       |
| 后端只存覆盖  | `sys_i18n_message` 只放被改过的 key，量极小，无需同步                   |
| 类型安全    | key 写错编译期即报错，不依赖运行时发现                                  |
| 离线兜底    | 后端不可用时按前端基线渲染，界面照常可用                                   |
| 运营在线改值  | 「国际化管理」页面改值即生效，无需前端发版                                  |
| 多级缓存    | 首次加载后缓存 30 分钟，写操作自动按语言前缀失效                             |
| 边界清晰    | `theme` / `form` / `dropdown` / `icon` / `request` 为 UI 框架文案，不允许被覆盖 |

## 2. 架构设计

### 2.1 后端架构

```
Controller (SysI18nController)
  |
  +-- /sys/i18n          -- 覆盖值管理接口（新增/修改/删除覆盖行）
  +-- /sys/i18n/page     -- 覆盖行分页查询
  +-- /sys/i18n/messages -- 前端获取覆盖值（公开只读，带缓存）

Service (SysI18nService)
  |-- add() / delete() / update()
  |-- 新增/更新前校验 (lang, msgKey) 唯一性

Manager (SysI18nManagerImpl extends BaseServiceImpl)
  |-- add() / delete() / modify() / getDtoById() / getPage()
  |-- getMessagesByLangAndModules() -- 按语言取覆盖值
  |-- existsByLangModuleKey() -- 重复校验

Entity (SysI18nMessage)
  |-- id, lang, moduleId, msgKey, msgValue, description, msgStatus
  |-- 覆盖行的 moduleId 恒为 NULL（不参与唯一性）
```

> 后端 Java 代码无需为覆盖模型做任何改动：`SysI18nCreateParam.moduleId` 本就可选，
> `existsByLangModuleKey` 的语义恰好是「(lang, msgKey, module_id 是否为 null)」。

### 2.2 前端架构

```
views/manage/i18n/
  |-- index.vue                          -- 管理页：前端目录 + 后端覆盖 的对照视图
  |-- modules/i18n-search.vue            -- 筛选（语言/关键词/命名空间/只看已覆盖）
  |-- modules/i18n-operate-drawer.vue    -- 设置某条 key 的覆盖值

locales/
  |-- index.ts          -- setupI18n + loadBackendMessages + OVERRIDABLE_NAMESPACES
  |                     -- + flattenMessages（管理页枚举本地 key 目录用）
  |-- locale.ts         -- 本地静态消息入口
  |-- langs/            -- zh-cn.ts / en-us.ts（完整目录与基线值）

service/api/
  |-- i18n.ts   -- 覆盖值 CRUD（/sys/i18n/*）
  |-- app.ts    -- fetchGetI18nMessages（前端启动时加载覆盖值）
```

### 2.3 缓存设计

```
前端请求 /sys/i18n/messages?lang=zh_CN
  |
  +-- MultiLevelCacheUtil.get(cacheKey)
      |
      +-- Caffeine L1 (本地 JVM 缓存)
      +-- Redis L2 (分布式缓存)
      |
      +-- 缓存未命中 -> 查询数据库 -> 写入缓存 (30分钟)
```

缓存 Key 格式：`i18n:messages:{lang}` 或 `i18n:messages:{lang}:{moduleCodes}`

### 2.4 缓存失效

| 操作      | 行为                                      |
|---------|-----------------------------------------|
| 新增/更新单条 | `evictByPrefix("i18n:messages:{lang}")` |
| 批量删除    | `evictByPrefix("i18n:messages:")`       |

**注意**：不再调用 `MultiLevelCacheUtil.clear()` 全量清除，避免影响其它业务缓存。

后端失效是即时的；**前端仍需刷新页面**才能看到新值（见 §7.5）。

## 3. 数据模型

### 3.1 功能模块表 (sys_module)

系统已有表。**i18n 已不再依赖它做分组** —— 覆盖行的 `module_id` 恒为 `NULL`。
该表仍服务于「功能模块管理」页面本身。

### 3.2 国际化消息表 (sys_i18n_message)

> **这张表存的是「覆盖值」，不是完整文案。** 没被运营改过的 key 在这张表里**没有行**。

| 字段          | 类型           | 说明                                             |
|-------------|--------------|------------------------------------------------|
| id          | BIGINT       | 主键                                             |
| lang        | VARCHAR(20)  | 语言标识，如 `zh_CN` / `en_US`（**下划线**，与前端 `zh-CN` 不同） |
| module_id   | BIGINT       | 分类标签，覆盖行恒为 `NULL`，不参与唯一性                        |
| msg_key     | VARCHAR(200) | 消息键，点号分隔，如 `common.add`；**必须存在于前端语言文件**          |
| msg_value   | TEXT         | 覆盖值                                            |
| description | VARCHAR(500) | 描述说明                                           |
| msg_status  | BOOLEAN      | 状态：`true` 启用，`false` 禁用（只有启用的会下发给前端）             |

### 3.3 唯一约束

```sql
CREATE UNIQUE INDEX uk_i18n_lang_msg_key
    ON sys_i18n_message (lang, msg_key);
```

覆盖模型下唯一性是「同语言同消息键」，`module_id` 不参与。

> 无需 `WHERE is_deleted = 0`：本表实体未标注 `@TableLogic`，**删除是物理删除**，
> 不会留下占位的软删行。「还原后再重新覆盖同一个 key」可以正常工作（已实测）。
> 注意对比 `sys_operation` —— 那个实体带 `@TableLogic`，它的唯一索引不加部分条件就会
> 撞约束，是另一处待修的既有问题。

### 3.4 消息键命名规范

```
{命名空间}.{功能}.{具体键}

命名空间只有四个（见 §7.4）：
  system   -- 系统级文案
  common   -- 通用操作与提示
  route    -- 路由/菜单标题
  page     -- 各业务页面文案

示例：
  system.title              -- 系统标题
  common.add                -- 通用新增
  page.manage.user.title    -- 用户管理页面标题
  page.manage.role.roleName -- 角色名称字段
```

## 4. 后端API

### 4.1 管理接口 (需登录)

| 方法   | 路径                 | 说明                            |
|------|--------------------|-------------------------------|
| POST | `/sys/i18n`        | 新增覆盖                          |
| POST | `/sys/i18n/delete` | 删除覆盖 (body: `{ids: []}`)       |
| POST | `/sys/i18n/update` | 更新覆盖                          |
| GET  | `/sys/i18n/{id}`   | 详情                            |
| GET  | `/sys/i18n/page`   | 覆盖行分页列表                       |

**新增/更新参数：**

```json
{
  "lang": "zh_CN",
  "moduleId": null,
  "msgKey": "common.add",
  "msgValue": "添加",
  "msgStatus": true
}
```

**注意：**

- `moduleId` 一律传 `null` —— 覆盖模型下唯一性是 `(lang, msgKey)`，模块不参与
- `msgKey` **必须已经存在于前端语言文件**，否则前端 `$t()` 编译不过，
  管理页也列不出它
- 这些接口管理的是**覆盖行**，不是「文案本身」

### 4.2 前端接口 (公开只读)

| 方法  | 路径                   | 说明               |
|-----|----------------------|------------------|
| GET | `/sys/i18n/messages` | 获取指定语言的**全部覆盖值** |

**参数：**

```
lang          -- 语言标识 (zh_CN / en_US)，需符合正则 ^[a-zA-Z]{2}([-_][a-zA-Z]{2})?$
moduleCodes   -- （v1.x 遗留，覆盖模型下不适用）它按 module_id 过滤，
                 而覆盖行的 module_id 恒为 NULL，存量库迁移后会返回空。
                 前端从未使用该参数 —— loadBackendMessages 只传 lang
```

> 实测：迁移前因历史镜像行仍带 `module_id`，`moduleCodes=system` 尚能返回结果；
> 执行覆盖迁移清空镜像行之后，同样的调用会返回空。

**响应：**

```json
{
  "code": "00000",
  "msg": "success",
  "data": {
    "lang": "zh_CN",
    "messages": {
      "common.add": "添加"
    }
  }
}
```

返回的是**覆盖值**，未覆盖的 key 不在此列 —— 它们由前端语言文件提供基线值。

### 4.3 错误码

| 错误码     | 说明            |
|---------|---------------|
| `20971` | 国际化消息不存在      |
| `20972` | 国际化消息已存在      |
| `20973` | 同语言同消息键已存在    |

## 5. 前端集成

### 5.1 初始化加载

前端应用在启动时自动加载后端覆盖值：

```typescript
// src/main.ts
import { setupI18n } from './locales';

async function setupApp() {
  // ...
  await setupI18n(app); // 异步合并后端覆盖值
  // ...
}
```

```typescript
// src/locales/index.ts
export async function setupI18n(app: App) {
  app.use(i18n);
  const currentLocale = i18n.global.locale.value as App.I18n.LangType;
  await loadBackendMessages(currentLocale);
}
```

### 5.2 语言切换

```typescript
// src/store/modules/app/index.ts
import { setLocale, loadBackendMessages } from '@/locales';

async function changeLocale(lang: App.I18n.LangType) {
  setLocale(lang);
  localStg.set('lang', lang);
  await loadBackendMessages(lang); // 重新拉取该语言的覆盖值
}
```

> 只有这两处会拉取后端覆盖值（启动 + 切语言）。**运营在管理页改完值后，
> 前端需要刷新页面才能看到。**

### 5.3 在组件中使用

与标准 vue-i18n 用法一致：

```vue
<template>
  <h1>{{ $t('system.title') }}</h1>
  <button>{{ $t('common.add') }}</button>
</template>
```

### 5.4 取值优先级

```
$t('common.add')
  1. 后端覆盖值（若该 key 有覆盖行且 msgStatus = true）
  2. 前端基线值（locales/langs/*.ts，总是存在）
```

### 5.5 本地文件是「完整目录」，不是「兜底」

**关键区别（与 v1.x 不同）**：前端语言文件不是"后端挂了才用"的兜底，而是：

- **key 的权威** —— 不在前端就编译不过，`$t()` 的签名依赖它
- **基线值的权威** —— 没有覆盖行时，页面显示的就是它
- **类型来源** —— `src/typings/app.d.ts` 的 `App.I18n.Schema` 与它严格同构

**不允许被覆盖的命名空间**：`theme`、`form`、`dropdown`、`icon`、`request`
（UI 框架级文案）。后端若返回这些命名空间的 key，`loadBackendMessages` 会跳过并打印告警。

**允许被覆盖的命名空间**：`system`、`common`、`route`、`page`
（前端常量 `OVERRIDABLE_NAMESPACES`，管理页只列出这四个）。

## 6. 管理后台操作

### 6.1 功能模块管理

**路径**：系统管理 → 功能模块

> i18n 已不再依赖功能模块做分组，但该页仍用于维护 `sys_module` 本身
> （其他业务可能引用）。

### 6.2 国际化文案管理

**路径**：系统管理 → 国际化管理

这一页是**前端 key 目录与后端覆盖值的对照视图**：

| 列      | 含义                        |
|--------|---------------------------|
| 消息键    | 来自前端语言文件（可复制）             |
| 前端基线值  | 语言文件里的值，只读                |
| 后端覆盖值  | 运营改过的值；显示「已覆盖」标签表示有覆盖行     |
| 操作     | 编辑（设置/修改覆盖值）、还原（删除覆盖行，回落基线） |

**操作步骤：**

1. 选语言（中文 / 英文）
2. 用关键词、命名空间或「只看已覆盖」缩小范围
3. 点「编辑」→ 抽屉里会同时显示**只读的消息键与基线值**，以及可编辑的覆盖值
4. 保存即为该 key 写入覆盖行；前端刷新后生效
5. 不想改了，点「还原」删掉覆盖行即可回落到基线；勾选多行可「批量还原」

**这一页没有「新增」** —— key 只能来自前端语言文件（见 §7.1）。

**最佳实践：**

- 覆盖值尽量只改措辞，不要改变语义（关键提示语改坏比改好容易）
- 改完提醒使用者刷新页面
- 非必要时不要覆盖 —— 覆盖行是一层额外的间接，会让「改了前端不生效」变得难排查

## 7. 开发规范

### 7.1 新增文案的流程

**key 的权威在前端语言文件**（`$t()` 的类型要求），所以新增文案从代码开始：

1. 在 `carlos-ui/src/locales/langs/zh-cn.ts` 与 `en-us.ts` 里加 key
2. 在 `carlos-ui/src/typings/app.d.ts` 的 `App.I18n.Schema` 里补类型声明
3. 组件里用 `$t('msgKey')`
4. **到此结束，不需要任何后端操作**

> 「国际化管理」页面**不能新增 key**：key 不在前端目录里 `$t()` 就编译不过，
> 而且那个页面也列不出它（它的 key 列表来自前端）。那个页面是用来**改值**的，见 7.4。

### 7.2 消息键命名规范

```
# 正确示例
system.title
common.addSuccess
page.manage.user.userName

# 错误示例
SystemTitle       # 驼峰命名不规范
system-title      # 中横线不便于嵌套
user_name         # 下划线不标准
```

### 7.3 缓存注意事项

- i18n 覆盖值缓存时间为 **30 分钟**
- 新增/修改/删除覆盖时，后端会自动按语言前缀失效对应缓存
- 不再使用全量 `clear()`，避免影响其它业务缓存

### 7.4 前端基线与后端覆盖

两层各司其职，**不是「两份都要维护」**：

| 层 | 职责 | 权威性 |
|---|---|---|
| 前端 `locales/langs/*.ts` | 完整 key 目录 + 基线值 + `$t()` 类型源 + 离线兜底 | key 与基线值 |
| 后端 `sys_i18n_message` | 只存被改过的 key 的覆盖值 | 覆盖值 |

运行时合并：`$t(key)` 的值 = **后端覆盖值 ?? 前端基线值**。

- **禁止**在后端配置 `theme`、`form`、`dropdown`、`icon`、`request` 命名空间下的 key ——
  这些是 UI 框架文案，始终以前端为准（后端若返回会被跳过并在控制台告警）
- 覆盖行是**叠加在基线之上的补丁**，不是替代品 —— **前端基线值不能删**，
  否则那些没被覆盖的 key 会全空

### 7.5 让覆盖生效

- 后端：新增/修改/删除会按语言前缀 `evictByPrefix` 失效缓存，无需等 30 分钟
- 前端：**需要刷新页面**（或切一次语言）—— `loadBackendMessages` 只在启动与切换语言时调用

### 7.6 从 v1.x（全量镜像）迁移

存量库执行：

```
carlos-integration/carlos-system/docs/02-design/database/sys_i18n_override_migration.sql
```

它做两件事：换唯一索引、**清空历史全量镜像行**。

第二步**不能省**：那批行在新模型下会被当成覆盖值，而它们的值取自当时的前端文件，
之后前端改过的文案会被这些陈旧覆盖**遮蔽**，表现为「改了前端但页面不变」。
清空不丢东西 —— 完整文案都在前端语言文件里（也在 git 里）。

## 8. 常见问题

### Q1: 前端切换语言后翻译未更新？

**A**: 检查：

1. 后端 `/sys/i18n/messages` 是否正常返回
2. `loadBackendMessages` 是否执行（启动与切语言时各一次）
3. 浏览器控制台是否有 401/403
4. 对应覆盖行的 `msgStatus` 是否为 `true`

### Q2: 改了前端语言文件，页面却没变？

**A**: 这是覆盖模型下最典型的现象 —— **该 key 存在后端覆盖行，覆盖值把基线值遮蔽了**。

1. 到「国际化管理」页面筛选「只看已覆盖」，看该 key 是否在列
2. 在列的话，点「还原」删掉覆盖行，即回落到你改的基线值

> 如果是从 v1.x 升级上来且**还没执行** `sys_i18n_override_migration.sql`，
> 表里可能躺着几百条全量镜像行，会让「改了前端不生效」大面积出现。
> 执行那个脚本即可（见 §7.6）。

### Q3: 新增了覆盖但前端不显示？

**A**:

1. 确认 `msgStatus = true`
2. 确认 `msgKey` 拼写与前端使用的一致（**区分大小写**）
3. 确认 key 首段属于可覆盖命名空间（`system`/`common`/`route`/`page`），
   否则会被 `loadBackendMessages` 跳过并告警
4. **刷新页面** —— 前端只在启动与切语言时拉取覆盖值

### Q4: 插入重复 key 时报什么错？

**A**: HTTP 409，错误码 `20973`，提示「同语言同消息键已存在」。
唯一索引 `uk_i18n_lang_msg_key` 提供最终保证。

### Q5: 后端不可用时前端会怎样？

**A**: 完全正常。所有 key 的基线值都在前端语言文件里，只是覆盖值不生效 ——
也就是说运营改过的措辞会暂时回到原始文案，界面功能不受影响。

### Q6: 消息键中的点号有什么含义？

**A**: 点号表示嵌套层级。后端返回的是 flat key（`common.add`），
前端合并时会转换成嵌套对象：

```json
{
  "common": {
    "add": "添加"
  }
}
```

这样可以直接用 `$t('common.add')` 访问。

### Q7: 批量删除会不会影响其它业务缓存？

**A**: 不会。批量删除仅按 `i18n:messages:` 前缀失效缓存，不会清空其它业务缓存。

### Q8: 运营想加一个新文案，怎么办？

**A**: 走 §7.1 的开发流程 —— 由开发在前端语言文件里加 key。
「国际化管理」页面**做不到**这件事：它列的 key 来自前端，
后端凭空加一条前端不知道的 key，`$t()` 编译不过。
