# ADR-002: 角色授权三机制语义与结算规则

> **状态**: 已接受
> **日期**: 2026-09-22
> **作者**: Carlos Team
> **相关参与者**: -

---

## 背景（Context）

当前模型中，"用户为什么拥有某角色"存在**三套并存机制**，且无文档定义其优先级与冲突规则：

| 机制 | 表 | 原意 |
|---|---|---|
| 部门默认角色 | `org_department_role.is_default_role` | 进部门自动获得 |
| 岗位默认角色 | `org_position_role.is_default` | 任职自动获得（"入职自动获得"） |
| 受限显式授权 | `org_user_role.dept_id` + `expire_time` | 部门内生效 + 限时 |

此外，`org_user_role` 的生效判定**未闭环**:`OrgUserRoleManagerImpl.listByUserId` 只按 `user_id` 过滤——过期的角色照样进 JWT，限定某部门生效的角色在全系统生效。字段设计了，规则没实现。

## 决策（Decision)

1. **`org_user_role` 是唯一生效的授权事实表**。token 签发（carlos-auth `OrgRemoteRoleProvider`)、数据权限结算（`OrgDataScopeHelper`）一律只读此表，不实时展开部门/岗位默认角色；
2. **派生路径**：岗位默认角色为主（任职驱动授权，"人因岗而有权")，部门默认角色为兜底（仅当用户无任何岗位默认角色时生效）。入职/调岗/调部门时按此顺序**结算并物化写入** `org_user_role`;
3. **`org_user_role.dept_id` 语义定稿为"作用域"**：该授权仅在指定部门范围内参与数据权限结算；`NULL` = 全局生效。它不是授权来源（授权来源是"谁在什么时候因为什么授予")，不用于 token 角色集过滤——token 中的角色码集合按未过期的全部授权签发；
4. **`expire_time` 语义定稿为"临时授权"**：过期即不生效，token 签发与数据权限结算都必须过滤；
5. **回收规则**：卸任/调出**不自动收回显式授权**（避免误删管理员手工授权）；派生授权的回收依赖来源标记（`source` 字段，后续增强项）区分。

**生效角色集结算公式**:

```
effective_roles(user, ctx) =
    { r | (user, r, dept_scope, expire) ∈ org_user_role,
          (expire IS NULL OR expire > now) }
```

token 角色集 = effective_roles 的 role_code 集合；数据权限结算时若 `dept_id` 非空，仅当操作目标部门匹配该作用域时该角色参与最宽 scope 计算。

## 备选方案（Options Considered)

### 方案A：实时展开（查询时动态合并三套机制）

- **优点**: 无物化，默认角色改配置立即生效
- **缺点**: 登录链路每次都要 join 三张表结算，性能差；"用户当前有什么角色"没有可审计的答案；三套机制的冲突规则仍需定义

### 方案B：物化结算（选定）——派生结果落 org_user_role

- **优点**: 生效事实可查询、可审计、可手工修正；token 签发路径不变（仍只读一张表）；冲突在写入时一次性解决
- **缺点**: 默认角色配置变更不追溯存量用户（需显式重算）；需要来源标记区分派生/显式（暂缺）

### 方案C：只保留一条派生路径（删部门默认角色）

- **优点**: 最简单
- **缺点**: "整个部门都应有某基础角色"是真实诉求（如"技术部成员都能看 GitLab")，删掉会把负担转嫁给管理员逐个授权

## 决策理由（Consequences)

### 正面影响

- "用户有什么角色、为什么有"有唯一可审计的答案（`org_user_role`);
- 三套机制各司其职不再打架：岗位驱动主派生、部门兜底、显式授权灵活补充；
- `expire_time`/`dept_id` 从死字段变为有明确定义的语义。

### 负面影响 / 风险

- 物化结算引入"配置变更不追溯存量"的语义，需在管理面提供"重算"操作；
- 回收规则保守（不自动收回显式授权），权限收紧依赖管理员主动操作；
- **已知限制（2026-09-22 安全评审登记）**：授权在会话中途过期后，已签发 token 中的角色码在 access token 剩余 TTL（默认 2h）内仍有效。过滤发生在登录/刷新时的角色解析。若需更短的收紧窗口，应缩短 token TTL 而非在请求期实时查库。

### 妥协与权衡

选择物化而非实时展开，核心原因是认证链路的性能与可审计性；部门默认角色保留为兜底是因为它是真实管理诉求。`source` 来源标记缺失是当前物化方案的最大短板，列为后续增强。

## 实施计划

- [x] `OrgUserRoleManagerImpl.listByUserId` 增加 `expire_time` 过滤（token 签发闭环，2026-09-22 完成；管理面全量查询走 `listAllByUserId`)
- [ ] `OrgDataScopeHelper` 结算时消费 `dept_id` 作用域（数据权限闭环）
- [ ] `assignPositions` 按结算规则物化岗位默认角色；加入部门时兜底部门默认角色
- [ ] `org_user_role` 增加 `source` 字段（1显式/2岗位派生/3部门派生），支持派生授权回收
- [ ] 管理面提供"按默认角色配置重算存量用户"操作
