# ADR-003: 权限资源与审计职责边界

> **状态**: 已接受
> **日期**: 2026-09-22
> **作者**: Carlos Team
> **相关参与者**: -

---

## 背景（Context）

PRD v1.0.0(2026-05-20）定义了 carlos-org 自建的两组能力，实现时均未落地，形成了文档与代码的漂移：

1. **权限资源**: PRD 定义了 `org_permission`（菜单/按钮/API/数据字段四类）+ `org_role_permission`；实现实际复用 carlos-system 的 `sys_operation`（按钮+API 两类），角色授权关联表为 `org_role_operation`(operation_id 指向 `sys_operation.id`)。org 模块内**不存在 org_permission 表/实体**；
2. **审计日志**: PRD 定义了 `org_operation_log`/`org_login_log`/`org_audit_record` 三张表；实现从未建设，审计能力已由独立模块 carlos-audit(ClickHouse 存储，已接入管理后台）承担。

漂移的后果：开发者按 PRD 找表找不到、权限类型对不上（PRD 四类 vs 实际两类）、"数据字段级权限"看似缺失实则有意不建。

## 决策（Decision)

1. **权限资源定义归 carlos-system**：菜单(`sys_menu`)、操作权限（`sys_operation`，按钮+API）由 system 模块统一维护；carlos-org 只持有授权关联（`org_role_operation`)，不建设 `org_permission` 表；
2. **"数据字段"级权限不落地为授权类型**：敏感字段（手机号/证件/邮箱）的脱敏由框架 translation/encrypt 能力与 VO 层承担，不进入角色-权限授权模型；
3. **审计职责归 carlos-audit**:carlos-org 不建设 `org_*_log` 表，操作/登录/敏感操作审计统一写入 carlos-audit；需求侧的审计诉求（PRD §3.5）视为已由 carlos-audit 承接，PRD 对应章节废弃；
4. **认证身份归属**:`org_user`（含 `pwd`）是认证身份的唯一存储；carlos-auth 经 Feign 只读访问，不复制存储用户或凭证；
5. **已知缺口登记**：动态路由模式下菜单可见性不受角色控制（`sys_menu.meta.roles` 为死字段、`RouteMetaVO` 无 roles),`data_scope=自定义(5)` 无规则引擎——两者为后续专项，不在本 ADR 解决。

## 备选方案（Options Considered)

### 方案A：按 PRD 补齐 org_permission 与审计三表

- **优点**: 文档与实现一致（以文档为准）
- **缺点**: 与 carlos-system 的 sys_menu/sys_operation 重复建设，菜单/操作双份维护必然再漂移；carlos-audit 已生产化，org 自建审计是倒退

### 方案B：以实现为准修订文档（选定）

- **优点**: 权限资源单一归属（system)、审计单一归属（audit)，符合模块职责划分；无重复建设
- **缺点**: PRD 需要修订；"数据字段权限"作为一个概念被放弃，需向需求方确认

## 决策理由（Consequences)

### 正面影响

- 权限资源、审计各自有唯一归属模块，消除跨模块双写风险；
- PRD 与实现重新对齐，后续开发者不再被误导；
- 缺口（角色级菜单可见性、自定义数据范围）被显式登记而非隐藏在"看似已实现"的字段里。

### 负面影响 / 风险

- org 对 system 形成数据依赖（`org_role_operation.operation_id` 引用 `sys_operation.id`)，跨模块无数据库外键，依赖应用层校验；
- "数据字段级权限"需求若未来被重新提起，需要新建授权载体而非复用 PRD 原设计。

### 妥协与权衡

接受跨模块引用（org_role_operation → sys_operation）而没有引入外键或冗余快照，是因为两模块同属一个部署单元、共用数据库，应用层校验成本低于分布式约束成本。
