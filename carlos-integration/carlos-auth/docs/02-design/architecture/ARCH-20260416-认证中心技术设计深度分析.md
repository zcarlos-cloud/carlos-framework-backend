## 问题2：网关如何识Token 类型（客户端凭证 vs 用户授权

### 核心问题本质

`/oauth2/token` 是统一端点，不`grant_type` 都走这里。网关拿JWT 后必须能区分

- **用户 Token**：有 `user_id`，代表具体用户，按用户权限控- **客户Token**：无 `user_id`，代表服应用，只能访问开API

### 当前框架的区分机制（代码级）

**客户Token**（`CustomizeClientOAuth2TokenCustomizer.java:66-84`）：

```json
{
  "sub": "third-party-service",
  "client_id": "third-party-service",
  "grant_type": "client_credentials",
  "token_type": "client_token"
}
```

**用户 Token**（`Oauth2JwtTokenCustomizer.java:107-175`）：

```json
{
  "sub": "zhangsan",
  "user_id": 10001,
  "username": "zhangsan",
  "role_ids": [1, 2],
  "authorities": "read,write,ROLE_1,ROLE_2"
}
```

识别规则：`token_type == "client_token"` 客户端凭证；`user_id != null` 用户授权

### 网关实现方案

**全局过滤器（推荐*

```java
@Component
@Order(-1)
public class TokenTypeGatewayFilter implements GlobalFilter {
    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        String token = extractBearerToken(exchange);
        if (token == null) return chain.filter(exchange);

        return jwtDecoder.decode(token).flatMap(jwt -> {
            String tokenType = jwt.getClaimAsString("token_type");
            String path = exchange.getRequest().getPath().value();

            if ("client_token".equals(tokenType)) {
                if (!path.startsWith("/api/open/")) {
                    return unauthorized(exchange, "客户端凭证不能访问用户资);
                }
                ServerHttpRequest req = exchange.getRequest().mutate()
                    .header("X-Client-Id", jwt.getClaimAsString("client_id"))
                    .header("X-Token-Type", "client").build();
                return chain.filter(exchange.mutate().request(req).build());
            }

            Long userId = jwt.getClaim("user_id");
            if (userId != null) {
                ServerHttpRequest req = exchange.getRequest().mutate()
                    .header("X-User-Id", userId.toString())
                    .header("X-Token-Type", "user").build();
                return chain.filter(exchange.mutate().request(req).build());
            }
            return unauthorized(exchange, "无效Token 类型");
        });
    }
}
```

### 深层设计建议：使JWT `aud` 约束

仅靠 `token_type` claim 是软约束，更安全的方式是使用 JWT 标准`aud` 字段

```json
{ "aud": ["open-api"] }           // 客户Token：只能访open-api
{ "aud": ["user-api", "open-api"] } // 用户 Token：可访问两```

网关验证 `aud` 是否包含当前服务标识，不匹配直接拒绝（RFC 7519 标准行为）

### 技术陷
**陷阱1：`token_type` JWT 标准字段冲突**
JWT 标准`token_type` 通常`Bearer`，当前框架在 Claims 里自定义`token_type: "client_token"` 是非标准用法。建议改`carlos_token_type` `principal_type` 避免混淆
**陷阱2：客户端 Token 不支refresh_token**
`BaseAuthenticationProvider.java:177` refresh_token 只颁发给用户 Token，客户端凭证模式需要重新申请
**陷阱3：Token 撤销范围**
`/oauth2/revoke` 只撤销Token 本身，不影响同一用户的其Token

## 问题3：多种登录场景的统一设计

### 场景矩阵

| 场景        | 推荐入口                    | 底层 GrantType         | 是否需要浏览器 |
|-----------|-------------------------|----------------------|---------|
| 账号密码登录    | `POST /auth/user/login` | 直接登录                 |       |
| 手机验证码登  | `POST /oauth2/token`    | `sms_code`           |       |
| 微信/钉钉扫码   | `GET /oauth2/authorize` | `authorization_code` |       |
| 单点登录(SSO) | `GET /oauth2/authorize` | `authorization_code` |       |
| 三方服务端调  | `POST /oauth2/token`    | `client_credentials` |       |
| 应用免密跳转    | 自定`/sso/ticket`       | `ticket`             |       |


### 各场景具体实
**1. 账号密码登录**（内部系统，不走 OAuth2 标准流程
```

POST /auth/user/login
{ "username": "admin", "password": "123456", "clientId": "web-app" }

```

**2. 手机验证码登*（已支持：`SmsAuthenticationProvider.java`
```

POST /oauth2/token
Authorization: Basic base64(client_id:secret)
grant_type=sms_code&phone=13800138000&sms_code=123456

```

**3. 微信/钉钉登录**（推荐：扩展 `grant_type=social`
```

// 前端拿到第三code POST /oauth2/token
grant_type=social&social_type=wechat&social_code=WECHAT_CODE

```

**4. 单点登录（SSO*

```

// 业务系统 A 未登跳转
302 https://auth.carlos.com/oauth2/authorize?
response_type=code&client_id=app-a&redirect_uri=...&state=xxx

// 用户已在 auth 登录（Session 有效）→ 访问业务系统 B 时无需再次输入密码

```

**5. 三方服务端调*

```

POST /oauth2/token
grant_type=client_credentials&scope=read
Authorization: Basic base64(client_id:secret)

```

**6. 免密跳转（应用管理→三方系统*

```java
// 应用管理模块生成一次Ticket
redis.set("sso:ticket:" + ticket, userId, 5, MINUTES);
// 返回跳转链接：https://third-party.com/login?ticket=xxx

// 三方系统验证 ticket
POST /sso/ticket/verify { "ticket": "xxx" }
// carlos-auth 验证通过后生成用Token 返回
```

### 关键设计决策

**决策1：密码登录是否走 `/oauth2/token`*
当前框架选择不走，原因：内部系统不需client_id/client_secret 约束，接口更简洁。但如果需要第三方客户端接入，则必须通过
`/oauth2/token`
**决策2：微钉钉`authorization_code` 还是自定`grant_type`*

- 浏览器（SPA/PCWeb）：推荐 `authorization_code`，浏览器自动跳转体验- App/小程序：推荐 `grant_type=social`，前端直接拿 code
  传给后端

### 技术陷

**陷阱1：SSO Session 的域名限*
`JSESSIONID` Cookie 只在当前域名有效。`auth.carlos.com` `app-a.carlos.com` 可共享（同根域），但跨域系统无法共享
Session，需要改OIDC token 透传方案
**陷阱2：扫码登录的竞态条*
微信扫码PC 端需要轮询状态，当前框架没有内置扫码状态机，需要在 `qr_code`
授权类型外单独设计状态流转（pending/scanned/confirmed/expired）
**陷阱3：不同登录入口的 Token Claims 一致*
`/auth/user/login` `/oauth2/token` 都使`OAuth2TokenGenerator`，但需要确`Oauth2JwtTokenCustomizer`
对两种路径都生效，否Claims 会不一致

## 问题1：授权码模式下，授权码是如何获得的？

### 核心认知纠正

授权码来`/oauth2/authorize`，而非 `/oauth2/token`。两个端点职责完全不同：

| 端点                  | 调用       | 返回              | 协议        |
|---------------------|----------|-----------------|-----------|
| `/oauth2/authorize` | 浏览器（用户代理 | 302重定向（code在URL | HTTP重定    |
| `/oauth2/token`     | 业务系统服务   | JSON（token在Body | HTTP POST |

### 完整授权码获取流

**第一阶段：获取授权码（浏览器参与*

```
浏览                   carlos-auth                  业务系统后端
                                                            GET /oauth2/authorize                                    ?response_type=code                                      &client_id=app-a                                         &redirect_uri=...                                        &state=random_csrf_token                                │──────────────────────────>                                                         检SecurityContext/Session    [未登录] 302 /login                                   ──────────────────────────                                POST /auth/user/login                                   │──────────────────────────>认证成功，写入SecurityContext    302 /oauth2/authorize                                 ──────────────────────────                                GET /oauth2/authorize                                   │──────────────────────────>生成一次性授权码(5分钟有效)                                redis: oauth2:code:{code}       302 redirect_uri                                       ?code=AbCdEf123                                          &state=random_csrf_token                                ──────────────────────────                                GET /callback?code=...                                  │──────────────────────────────────────────────────────────>```

**第二阶段：用授权码换Token（服务端对服务端*

```

### 关键设计细节（结合代码）

**1. 授权码的存储机制**

`RedisOAuth2AuthorizationService` 中，授权码存储在
```

oauth2:code:{code_value} OAuth2Authorization 序列化对TTL =
5分钟（AuthorizationServerProperties.authorizationCodeTimeToLive```

授权码一旦被使用就立即删除，这是防重放的关键
**2. state 参数的作用（CSRF防护*

浏览器发起请求时携带 `state=random_csrf_token`，授权码回调时业务系统必须验state 与发起时一致，防止 CSRF 攻击
**3. 为什么授权码要经过浏览器*

- Token 不经过浏览器（防止被浏览器历日志泄露- 授权码经过浏览器（但一次性、短期有效，即使泄露危害有限-
  业务系统服务端持client_secret（浏览器不知secret
  **4. 当前框架的登录态维*

`carlos-auth` 使用 Spring Security Session 维持登录态，浏览器携`JSESSIONID` Cookie。这SSO 的基础：用户在 auth
登录一次，访问其他系统Session 仍有效，无需再次输入密码

### 技术陷

**陷阱1：redirect_uri 必须精确匹配**
注册客户端时配置`redirect_uri` 必须与请求中的完全一致（包括尾部斜杠）
**陷阱2：前后端分离场景的特殊处*
在授权码模式下，登录完成后需要重定向`/oauth2/authorize`，而不是直接返token，需要前端配合处理
**陷阱3：SPA 应用必须使用 PKCE**
纯前端应用无法安全存`client_secret`，必须启PKCE

```yaml
clients:
  - client-id: spa-app
    require-proof-key: true
```
