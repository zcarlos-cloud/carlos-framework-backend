## 三、核心设计：认证安全等级 (AAL) 分层

参考 NIST SP 800-63B，将认证划分为三个等级，根据风险动态选择：

| 等级       | 要求                           | 适用场景      | 触发条件          |
|----------|------------------------------|-----------|---------------|
| **AAL1** | 单因素（密码 OR 短信 OTP OR Passkey） | 普通浏览、内网   | 低风险 + IP 白名单内 |
| **AAL2** | 双因素（密码 + TOTP/Passkey/短信OTP） | 企业默认、敏感数据 | 默认策略 OR 中风险   |
| **AAL3** | 硬件密码学认证器（FIDO2 安全密钥）         | 管理员、财务、合规 | 角色强制 OR 高风险   |

### 3.1 风控→AAL 动态提升（Step-Up Authentication）

```java
public enum RiskLevel {
    LOW,      // 无感通过，不需验证码，AAL1 即可
    MEDIUM,   // 需要滑块验证码，维持当前 AAL
    HIGH,     // 强制 MFA step-up 到 AAL2+
    CRITICAL  // 阻断，拒绝登录，触发安全告警
}
```

### 3.2 决策链路

```
请求进入 → 设备指纹采集 → 风控打分
  │
  ├── score < 30 (LOW):     无感通过
  ├── 30 ≤ score < 60 (MEDIUM): 弹出滑块验证码
  ├── 60 ≤ score < 85 (HIGH):   强制 MFA（TOTP/短信/Passkey）
  └── score ≥ 85 (CRITICAL):    拒绝 + 告警 + 账号临时冻结
```

### 3.3 NIST 800-63B 关键密码要求（2020 修订）

- 最低 8 位长度（建议 ≥ 64 位上限放宽，鼓励长密码/口令句）。
- **取消复杂度强制要求**（不再强制大小写+数字+符号组合）。
- **取消定期强制更换**（除非有泄露证据）。
- **必须做泄露密码检查**（HaveIBeenPwned API / NIST 泄露密码库）。
- 允许所有可打印 ASCII 与空格，支持 Unicode。
- 失败次数限制 + 锁定策略 + 异常告警（而非简单账号锁定，避免 DoS）。

### 4.3 登录预校验设计要点

1. **账号存在性校验**：输入手机号/邮箱后失焦请求 `/auth/pre-check`，返回"账号存在/不存在"。
    - **防枚举攻击**：对"账号不存在"也返回模糊提示，并对未注册账号下发等长响应避免时序侧信道。
2. **风控预判**：基于设备指纹 + IP 信誉 + 历史行为，决定是否需要挑战。
3. **是否需要 MFA 预判**：账号是否绑定 TOTP/Passkey，决定后续挑战链。
4. **限流**：按 `IP + 账号 + 设备指纹` 三维限流，滑动窗口 1 分钟 5 次失败即触发验证码。
5. **响应恒定化**：预校验接口响应时间需 padding 到统一时长，防时序侧信道。

## 五、Token 体系重设计

### 5.1 Token 生命周期矩阵

| Token 类型                 | 存储方式                            | 生命周期             | 续期策略                | 撤销方式                        |
|--------------------------|---------------------------------|------------------|---------------------|-----------------------------|
| **Access Token (JWT)**   | 内存 / HttpOnly Cookie (BFF)      | **15 分钟**        | 通过 Refresh Token 续签 | Redis 黑名单（jti）              |
| **Refresh Token**        | HttpOnly Secure SameSite Cookie | **7 天** (滑动续期)   | Rotation（每次使用签发新的）  | 直接删除 Redis 中的 Authorization |
| **ID Token (OIDC)**      | 前端解析后丢弃                         | 与 Access Token 同 | 不续期                 | N/A                         |
| **MFA Token**            | 内存                              | **5 分钟**         | 不续期，一次性             | 验证后立即失效                     |
| **Trusted Device Token** | HttpOnly Secure Cookie          | **30 天**         | 每次 MFA 后续签          | 用户手动注销                      |
| **QRCode Session**       | Redis                           | **120 秒**        | 不续期                 | 使用/过期后删除                    |

### 5.2 Refresh Token Rotation + 家族检测

```
用户首次登录 → 签发 RT₁
用 RT₁ 换新 AT → 同时签发 RT₂，RT₁ 失效
用 RT₂ 换新 AT → 同时签发 RT₃，RT₂ 失效
...
若攻击者窃取 RT₁ 后使用：
  - 合法用户用 RT₂ 换 AT → 正常
  - 攻击者用 RT₁（已失效）→ 检测到"已废弃 token 被再次使用"
  - 触发整个家族（RT₁ 全部衍生）撤销，强制重新登录
```

**实现要点**：

```java
/**
 * Refresh Token 安全策略
 *
 * 每次使用 refresh_token 换取新的 access_token 时：
 * 1. 签发全新的 refresh_token（RT₂），原 RT₁ 立即失效
 * 2. 将 RT₁ 标记为"已使用"（保留 24h 用于检测泄露）
 * 3. 如果"已使用"的 RT₁ 再次被使用 → 检测到泄露
 *    → 撤销整个 Token 家族，强制重新登录
 */
public class RefreshTokenRotationStrategy {
    // 家族 ID：同一次登录产生的所有 RT 共享一个 familyId
    // 检测：已废弃的 RT 被重用 → 整个 family 全部撤销
}
```

## 六、扫码登录完整设计

### 6.1 状态机

```
┌──────────┐   生成二维码    ┌──────────┐
│  INIT    │───────────────►│ PENDING  │ (TTL = 120s)
└──────────┘                └────┬─────┘
                                 │
              ┌──────────────────┼───────────────┐
              │                  │               │
              ▼                  ▼               ▼
        ┌──────────┐     ┌──────────┐    ┌──────────┐
        │ EXPIRED  │     │ SCANNED  │    │ CANCELED │
        │ (超时)   │     │(待确认)  │    │(用户取消) │
        └──────────┘     └────┬─────┘    └──────────┘
                              │
                    ┌─────────┼─────────┐
                    ▼                    ▼
              ┌──────────┐        ┌──────────┐
              │CONFIRMED │        │ CANCELED │
              │(签发Token)│        │(APP取消) │
              └──────────┘        └──────────┘
```

### 6.2 接口设计

```
// PC 端
GET  /auth/qrcode/generate          → {qrcodeId, qrcodeUrl, expireAt}
GET  /auth/qrcode/status/{id}       → SSE 流 (推送状态变更)

// APP 端（已登录用户）
POST /auth/qrcode/scan              → {qrcodeId} + Bearer Token
POST /auth/qrcode/confirm           → {qrcodeId} + Bearer Token
POST /auth/qrcode/cancel            → {qrcodeId} + Bearer Token
```

### 6.3 通信方式对比

| 方式            | 实时性        | 服务端压力    | 实现          |
|---------------|------------|----------|-------------|
| **短轮询**       | 低（1–2s 延迟） | 高（海量空请求） | 简单          |
| **长轮询**       | 较高         | 中        | 中等          |
| **WebSocket** | 高          | 低        | 复杂（需维护连接）   |
| **SSE**       | 高（单向）      | 低        | 简单（HTTP 复用） |

**推荐**：SSE 为主 + 短轮询兜底（SSE 断连时降级）。

### 6.4 二维码安全设计

1. **一次性**：每个二维码绑定一个 `qrcode_id`（UUID + 随机数），使用后立即失效。
2. **短 TTL**：60–120 秒过期，过期后前端展示"二维码已失效，点击刷新"。
3. **签名**：二维码内容 = `qrcode_id + expires_at + HMAC(server_secret, qrcode_id|expires_at)`，防止伪造。
4. **防重放**：`qrcode_id` 全局唯一，确认后状态机不可逆（`CONFIRMED` 后再扫无效）。
5. **防中间人**：扫码后 APP 端需携带自身 Token + `qrcode_id` 调用确认接口，服务端校验 APP 用户身份 + 二维码归属。
6. **限流**：单 IP / 单设备生成二维码频次限制，防扫描爆破。

**二维码内容**：通常是一个短 URL（如 `https://login.carlos.com/q/{qrcode_id}`），APP 扫码后打开该 URL，APP 内置浏览器携带 APP
Token 完成确认。

## 八、SSO 演进方案（三阶段）

### 8.1 阶段一（当前 → 2周）：JSON API + Session 双发

```java
// 登录成功后，除返回 JWT Token 外，同时在 auth 域种下 Session Cookie
// 这样 /oauth2/authorize 检查时能识别用户已登录
@PostMapping("/auth/user/login")
public Result<LoginResponse> login(...) {
    LoginResponse response = loginService.login(request);

    // 种 Session（为 SSO 做准备）
    httpSession.setAttribute("SPRING_SECURITY_CONTEXT", securityContext);

    return Result.success(response);
}
```

**效果**：前端无需改动，但 auth 域已有 Session，为后续 SSO 铺路。

### 8.2 阶段二（2-4周）：补齐 `/login` 表单页 + 授权码模式

```java
// 启用 formLogin
http.formLogin(form -> form
    .loginPage("/login")
    .loginProcessingUrl("/login")
    .successHandler(savedRequestAwareSuccessHandler())  // 回到 /oauth2/authorize
    .failureHandler(jsonFailureHandler())
);
```

**效果**：新系统接入走 `/oauth2/authorize` → `/login` → 回调，实现真正 SSO。

### 8.3 阶段三（1-3月）：全面 OIDC + Back-Channel Logout

- `carlos-ui` 接入 `oidc-client-ts`。
- 所有新系统走标准 OIDC Discovery。
- Back-Channel Logout 推送：登出时 auth 主动通知所有 RP。
- `/auth/user/login` 保留但标记为内部端点（`@Deprecated` 路线）。

### 8.4 SSO 必须满足的条件

1. **浏览器在 IdP 域下有共享的 Session Cookie**：`/oauth2/authorize` 流程通过浏览器重定向，天然满足；`/auth/user/login` 是
   AJAX，无法满足（AJAX 不能跨域写 Cookie）。
2. **所有系统都信任同一个 IdP**：系统 A、B、C 都跳转 `carlos-auth` 的 `/oauth2/authorize`，而不是各自写自己的登录接口。
3. **Token 可以统一撤销**：用户在系统 A 登出，系统 B 的 Token 也应失效（通过 `/logout` + Token 黑名单实现）。

### 8.5 单点登出：Front-Channel vs Back-Channel

| 方式                            | 机制                                                                                | 优势        | 劣势             |
|-------------------------------|-----------------------------------------------------------------------------------|-----------|----------------|
| **Front-Channel Logout**      | IdP 通过 `<iframe>` 通知各 RP 登出                                                       | 实现简单      | 依赖浏览器、易被拦截、不可靠 |
| **Back-Channel Logout (RFC)** | IdP 直接调用 RP 的 back-channel logout 端点，携带 `logout_token`（含 `sub`/`sid`/`iat`/`jti`） | 可靠、不依赖浏览器 | RP 需实现接收端点     |

**推荐**：优先 Back-Channel Logout（Spring Authorization Server 1.1+ 已支持），Front-Channel 作为补充。`logout_token` 必须验证签名、
`iss`、`aud`、`iat`、`jti` 唯一性（防重放）。

## 九、密码安全修复方案

### 9.1 为什么不能用对称加密（AES/SM4）存密码

- 对称加密是**双向可逆**的，密钥泄露 = 所有密码明文泄露。
- 密钥与加密数据同库存储时，数据库泄露即密钥泄露，等于没加密。
- 密钥管理（HSM/KMS）成本高，且仍有"可还原"的根本问题。
- 密码存储要的是**不可逆**，对称加密从原理上就不对位。

### 9.2 OWASP 2024 推荐哈希算法优先级

| 优先级   | 算法           | 适用                              |
|-------|--------------|---------------------------------|
| ⭐⭐⭐⭐⭐ | **Argon2id** | 新系统首选（PHC 竞赛冠军，抗 GPU/ASIC，内存硬度） |
| ⭐⭐⭐⭐  | scrypt       | 次选（内存硬度，但不如 Argon2 现代）          |
| ⭐⭐⭐   | bcrypt       | 遗留系统（72 字节长度限制）                 |
| ⭐⭐    | PBKDF2       | FIPS 合规场景                       |

### 9.3 Argon2id 推荐参数（OWASP 2024）

| 参数               | 推荐值                    |
|------------------|------------------------|
| 内存（memory）       | ≥ 19 MiB（建议 46–64 MiB） |
| 迭代次数（iterations） | ≥ 2（内存高时可 1）           |
| 并行度（parallelism） | 1（或 CPU 核心数）           |
| 哈希长度             | 32 字节                  |
| 盐长度              | 16 字节                  |

**Pepper**：可选，存于数据库之外（环境变量/KMS）的密钥，`hash = Argon2id(password + salt, pepper)`，数据库泄露时仍需破 pepper。

### 9.4 存储迁移方案（SM4 → Argon2id）

```java
/**
 * 密码编码器迁移策略
 *
 * 使用 DelegatingPasswordEncoder，根据前缀识别算法：
 * - {sm4}xxx    → 旧格式，登录时自动迁移到 argon2
 * - {argon2}xxx → 新格式
 * - {bcrypt}xxx → 过渡格式
 */
@Bean
public PasswordEncoder passwordEncoder() {
    Map<String, PasswordEncoder> encoders = new HashMap<>();
    encoders.put("argon2", new Argon2PasswordEncoder(16, 32, 1, 46 * 1024, 3));
    encoders.put("bcrypt", new BCryptPasswordEncoder());
    encoders.put("sm4", new LegacySm4PasswordEncoder()); // 仅解密，不编码

    DelegatingPasswordEncoder delegate = new DelegatingPasswordEncoder("argon2", encoders);
    return delegate;
}
```

**迁移策略**：用户下次登录时，验证 SM4 密码正确后，自动用 Argon2id 重新哈希并更新。无需强制所有用户改密。

### 9.5 密码强度策略（NIST 800-63B）

```yaml
carlos:
  auth:
    password:
      min-length: 8
      max-length: 128
      require-complexity: false    # NIST 800-63B: 不强制复杂度组合
      check-pwned: true            # HaveIBeenPwned API (k-匿名)
      history-count: 5             # 禁止重用最近 5 次密码
      max-age-days: 0              # 0=不强制过期 (NIST 推荐)
      strength-estimator: zxcvbn   # 密码强度估算算法
      min-strength-score: 3        # zxcvbn 最低得分 (0-4)
```

### 9.6 密码传输加密

**行业争议**：

- HTTPS 已加密整个传输层，前端再 RSA/SM2 加密"看似多余"。
- 但前端加密是**纵深防御**：防 TLS 终止于 LB/CDN 时的明文日志、防 WAF 抓包记录密码、防服务器日志误记密码、合规要求（国密
  SM2）。

**推荐方案**：

- 默认 HTTPS 即可（HSTS + TLS 1.3）。
- 高安全场景额外做前端 SM2/RSA 公钥加密（公钥从后端动态获取，定期轮换私钥）。
- **国密合规场景**：前端 SM2 加密 + 后端 SM2 解密 + Argon2id 哈希存储（不能用 SM4 存密码）。

### 9.7 密码全生命周期

- **过期**：NIST 不再推荐强制定期更换（除非有泄露证据）。可在合规要求下保留 90 天策略。
- **历史**：改密时禁止重用最近 N 次（如 5 次）历史密码（历史哈希保留）。
- **重置/找回**：邮件/短信一次性 Token（短 TTL + 一次性 + 签名），重置后失效所有会话。
- **改密后**：强制所有会话失效 + 所有 Refresh Token 撤销 + 可信设备清空。

## 十、MFA 完整集成方案

### 10.1 MFA 方法优先级

| 方法                              | 优先级   | 实现状态     | 安全等级     |
|---------------------------------|-------|----------|----------|
| **Passkey/WebAuthn**            | ⭐⭐⭐⭐⭐ | 待开发      | AAL3     |
| **TOTP (Google Authenticator)** | ⭐⭐⭐⭐  | 骨架已有，待完善 | AAL2     |
| **短信 OTP**                      | ⭐⭐⭐   | 已有       | AAL2 (弱) |
| **邮件 OTP**                      | ⭐⭐    | 已有       | AAL1     |
| **恢复码**                         | 降级    | 骨架已有     | N/A      |

### 10.2 TOTP 原理

`TOTP = Truncate(HMAC-SHA1(K, floor(now/30))) mod 10^6`，K 为共享密钥，30 秒时间步长，6 位数字。注册时生成 secret + QR
Code（otpauth URI），用户扫码录入。

### 10.3 MFA 触发规则

```java
public boolean shouldRequireMfa(UserInfo user, RiskContext risk) {
    // 1. 角色强制：管理员/财务必须 MFA
    if (user.hasRole("admin", "finance")) return true;

    // 2. 风控要求：高风险必须 MFA
    if (risk.getLevel() == RiskLevel.HIGH) return true;

    // 3. 用户已启用 MFA：常规验证
    if (user.isMfaEnabled()) return true;

    // 4. 可信设备豁免
    if (isOnTrustedDevice(risk.getDeviceFingerprint(), user.getId())) return false;

    // 5. 企业策略：全员 AAL2
    if (tenantPolicy.isEnforceMfa()) return true;

    return false;
}
```

### 10.4 恢复码设计

- 注册 MFA 时生成 8–10 个，每个 8–16 字符（如 `ABCD-1234-EFGH-5678`）。
- 单次使用，使用后哈希删除。
- 存储为 Argon2id 哈希（同密码）。
- 用尽前提示重新生成。

### 10.5 受信任设备

```sql
CREATE TABLE auth_trusted_device (
    id BIGINT PRIMARY KEY,
    user_id BIGINT NOT NULL,
    device_fingerprint VARCHAR(128) NOT NULL,
    device_name VARCHAR(128),           -- "Chrome on Windows 11"
    last_used_at DATETIME NOT NULL,
    last_ip VARCHAR(45),
    last_location VARCHAR(128),
    trust_expires_at DATETIME NOT NULL, -- 30天后过期
    created_at DATETIME NOT NULL,
    UNIQUE KEY uk_user_device (user_id, device_fingerprint)
);
```

- MFA 通过后签发 `trusted_device_token`（30 天），存 HttpOnly Secure SameSite=Strict Cookie。
- 后续该设备跳过 MFA，但**敏感操作仍需 step-up**。
- Cookie 绑定 `device_id` + 设备指纹（UA/IP 段哈希），篡改即失效。
- 用户可在"已登录设备"页查看与远程注销。

## 十五、核心设计原则总结

1. **认证唯一入口**：所有认证收敛到 `carlos-auth`，`carlos-org` 不再代理登录。
2. **风控前置**：认证前先评估风险，动态决定挑战强度。
3. **AAL 分层**：不是所有场景都需要最强认证，按风险匹配等级。
4. **不可逆存储**：密码用 Argon2id 哈希，SM4 仅用于传输。
5. **Token 短命**：Access 15min + Refresh Rotation，泄露窗口最小化。
6. **MFA 渐进式**：不强制所有人每次 MFA，可信设备可跳过。
7. **统一身份源 SPI**：新增登录方式 = 新增一个 `IdentityProvider`，不改核心。
8. **SSO 标准化**：最终目标是 OIDC 授权码模式，`/auth/user/login` 是过渡。
9. **审计全覆盖**：每次认证事件（成功/失败/MFA/登出）都异步入库。
10. **纵深防御**：HTTPS + SM2 传输加密 + 风控 + 限流 + 验证码 + MFA + Token 撤销。
