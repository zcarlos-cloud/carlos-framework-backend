# Carlos Gateway 过滤器执行顺序文档

> **文档说明**：本文档描述 carlos-gateway 模块中所有 GlobalFilter 的执行顺序及如此安排的原因。
> 所有过滤器的顺序统一在 `GlobalFilterOrder` 接口中定义，严禁在过滤器类中硬编码数字。
>
> 最后更新：2026-06-06

---

## 一、执行顺序总览

### 1.1 GlobalFilter 执行顺序（从小到大）

| 阶段     | 顺序        | 过滤器                                     | 类型                   | 是否可禁用 | 关键依赖                                  |
|--------|-----------|-----------------------------------------|----------------------|-------|---------------------------------------|
| 可观测性基础 | **-9000** | `RequestTracingFilter`                  | GlobalFilter         | 是     | 无（最先执行）                               |
| 可观测性基础 | **-8500** | `MetricsFilter`                         | GlobalFilter         | 是     | `RequestTracingFilter`                |
| 准入控制   | **-8000** | `UnifiedWhitelistFilter`                | GlobalFilter         | 是     | `RequestTracingFilter`                |
| 准入控制   | **-7900** | `IdentityHeaderSanitizeFilter`          | GlobalFilter         | 否     | `UnifiedWhitelistFilter`              |
| 安全防护   | **-7000** | `WafFilter`                             | GlobalFilter         | 是     | `UnifiedWhitelistFilter`              |
| 安全防护   | **-6500** | `ReplayProtectionFilter`                | GlobalFilter         | 是     | `UnifiedWhitelistFilter`              |
| 流量控制   | **-6000** | `CarlosRateLimiterGatewayFilterFactory` | GatewayFilterFactory | 是     | 无                                     |
| 认证授权   | **-5000** | `OAuth2AuthenticationFilter`            | GlobalFilter         | 是     | `WafFilter`, `ReplayProtectionFilter` |
| 认证授权   | **-4500** | `OAuth2AuthorizationFilter`             | GlobalFilter         | 是     | `OAuth2AuthenticationFilter`          |
| 路由准备   | **-3000** | `GrayReleaseFilter`                     | GlobalFilter         | 是     | `OAuth2AuthenticationFilter`          |
| 路由准备   | **-2000** | `PathPrefixFilter`                      | GlobalFilter         | 是     | 无                                     |
| 路由准备   | **-1000** | `RequestTransformFilter`                | GlobalFilter         | 是     | `PathPrefixFilter`                    |
| 上下文传递  | **-450**  | `IdentityAssertionSignFilter`           | GlobalFilter         | 是     | `OAuth2AuthenticationFilter`          |
| 响应优化   | **100**   | `ResponseCacheFilter`                   | GlobalFilter         | 是     | 无                                     |
| 访问日志   | **1000**  | `AccessLogFilter`                       | GlobalFilter         | 否     | 所有前置过滤器                               |

### 1.2 与 Spring Cloud Gateway 内置过滤器的相对位置

```
自定义过滤器范围: -10000 ~ 10000

NettyWriteResponseFilter:        -1
ReactiveLoadBalancerClientFilter: 10150
RouteToRequestUrlFilter:         10000
NettyRoutingFilter:              Integer.MAX_VALUE
ForwardRoutingFilter:            Integer.MAX_VALUE
```

**说明**：所有自定义全局过滤器均安排在 `-10000 ~ 10000` 之间，确保在 SCG 内置路由过滤器之前或日志记录范围内执行。

## 二、各阶段详细说明

### 阶段一：可观测性基础

#### 1. RequestTracingFilter (order = -9000)

**作用**：

- 从请求头提取或生成 Request ID（业务追踪）
- 从 B3 头提取或新建 Trace ID（分布式链路追踪）
- 将追踪信息注入下游请求头，并在响应头中返回

**为什么最先执行**：
后续所有过滤器和下游微服务都依赖 `traceId` 和 `requestId` 进行链路追踪和日志关联。如果 Tracing 不在最前面，被拒绝的请求将无法被追踪到。

**技术实现**：基于 Brave Tracer，支持 B3 传播协议。

---

#### 2. MetricsFilter (order = -8500)

**作用**：

- 基于 Micrometer 记录请求 Counter、Latency Timer、Active Requests Gauge
- 按状态码分类统计（2xx/4xx/5xx/限流/拦截）
- 支持路径模式提取，降低 Prometheus 标签基数

**为什么紧跟 Tracing**：
使用 `doFinally` 模式，需要在过滤链进入后立即启动计时。无论请求被后续哪个过滤器拒绝（WAF、限流、认证失败等），指标都会被完整记录。

**技术实现**：Counter/Timer 实例缓存 + 路径模式提取（UUID/数字ID替换为 `{id}`）。

---

### 阶段二：准入控制

#### 3. UnifiedWhitelistFilter (order = -8000)

**作用**：

- 统一检查全局、认证、WAF、防重放、限流、路径前缀剥离等各类白名单
- 将匹配结果存入 `Exchange Attributes`，供后续过滤器直接读取
- 使用 `ConcurrentHashMap` 缓存匹配结果，避免重复的 Ant 路径匹配

**为什么在这个位置**：
在 WAF、防重放、认证等过滤器之前执行，实现"一次匹配，多处使用"。如果放在安全层之后，白名单内的路径会被无意义地检查多遍。

**技术实现**：Ant 风格路径匹配 + 短期缓存（上限 10000 条）。

---

### 阶段三：安全防护

#### 4. WafFilter (order = -7000)

**作用**：

- SQL 注入检测（预编译 Pattern + BitSet 快速字符检查）
- XSS 攻击检测
- 路径遍历和敏感文件访问检测
- 命令注入检测
- CSRF Token 验证

**为什么尽早执行**：
WAF 是网关的第一道防线，越早拦截恶意请求，越能减少后续认证、鉴权、后端调用的无意义开销。

**技术实现**：ThreadLocal Matcher 缓存 + BitSet 快速预检 + 请求体大小限制。

---

#### 5. ReplayProtectionFilter (order = -6500)

**作用**：

- 验证请求时间戳（5分钟容差）
- 检查 Nonce 唯一性（Redis 存储，防止重放）
- 验证 HMAC-SHA256 请求签名

**为什么在 WAF 之后**：
WAF 是更轻量的正则规则匹配，防重放需要验证签名（涉及字符串拼接、HMAC 计算）和查 Redis，开销更大。先通过 WAF
过滤明显的恶意流量，再对"看起来正常"的请求进行重放验证。

**技术实现**：ThreadLocal Mac 实例缓存 + HexFormat（JDK 17+）优化。

---

### 阶段四：流量控制

#### 6. CarlosRateLimiterGatewayFilterFactory (路由级)

**作用**：

- 基于 Redis 令牌桶算法的限流
- 支持 IP/USER/API/COMBINED 多种 KeyResolver 策略
- 黑名单/白名单机制
- 统一 ErrorResponse 格式

**为什么放在认证之前**：
限流放在认证之前，可以保护认证服务本身免受暴力破解、Token 刷接口等攻击。如果放在认证之后，攻击者可以无限制地尝试认证接口。

**注意**：这是 `GatewayFilterFactory`（路由级），非 `GlobalFilter`，其顺序由路由配置和 SCG 内部机制决定。

---

### 阶段五：认证授权

#### 7. OAuth2AuthenticationFilter (order = -5000)

**作用**：

- 统一处理 JWT 和 Opaque Token 认证
- 从 Authorization 头、自定义 Token 头、Query 参数提取 Token
- 验证 Token 有效性，构建 UserContext
- 将用户上下文注入请求头和 Exchange Attributes

**为什么在安全层和限流之后**：
认证是相对昂贵的操作（可能需要远程验证 Token），应该先通过 WAF、防重放、限流过滤掉非法/过量请求，再对合法的请求进行认证。

**技术实现**：TokenValidator 抽象 + 统一白名单复用。

---

#### 8. OAuth2AuthorizationFilter (order = -4500)

**作用**：

- RBAC（基于角色）或 ABAC（基于属性）权限控制
- 使用 Caffeine 缓存用户权限（5分钟过期）
- 缓存权限匹配结果（1分钟过期）

**为什么在 Authentication 之后**：
鉴权必须依赖认证的结果——`exchange.getAttribute(AuthConstant.USER_CONTEXT)`。如果认证未通过或没有 userContext，鉴权直接返回
401。

**技术实现**：Caffeine 双级缓存（权限缓存 + 匹配结果缓存）。

---

### 阶段六：路由准备

#### 9. GrayReleaseFilter (order = -3000)

**作用**：

- 支持基于用户、IP、权重、请求头的灰度策略
- 使用 MurmurHash3 计算哈希，选择灰度实例
- 设置灰度标记头传递给下游

**为什么在路由之前**：
灰度发布需要在路由决策之前确定"请求应该去灰度实例还是正式实例"。如果放在路由之后，请求已经被转发，无法再改变目标实例。

**技术实现**：MurmurHash3 + ThreadLocalRandom + Caffeine 策略缓存。

---

#### 10. PathPrefixFilter (order = -2000)

**作用**：

- 校验请求路径是否以配置的前缀开头（如 `/api/v1`）
- 剥离前缀后转发给后端服务（`/api/v1/org/users` → `/org/users`）

**为什么在路由之前**：
路径前缀剥离必须在路由匹配之前完成。如果 RouteToRequestUrlFilter（order=10000）先执行，它会基于原始路径进行路由匹配，导致路由错误。

**技术实现**：前缀校验 + 路径重写，白名单路径跳过。

---

#### 11. RequestTransformFilter (order = -1000)

**作用**：

- API 版本控制（从 Header 或 URL 路径提取版本）
- 路径重写（预编译 Pattern 缓存）
- Header 转换（添加/替换/删除）
- 添加网关标识和转发时间戳

**为什么在 PathPrefix 之后**：
先完成标准的路径前缀剥离（如 `/api/v1`），再执行自定义的路径重写和 Header 转换。这样转换规则可以基于"已剥离前缀"的路径编写，更简洁。

**技术实现**：预编译 Pattern 缓存 + 单次 `request.mutate()` 合并所有修改。

---

### 阶段七：上下文传递

#### 12. IdentityAssertionSignFilter (order = -450)

**作用**：

- 从 Exchange Attributes 读取 `userContext`（由 OAuth2AuthenticationFilter 设置）
- 用共享密钥（HMAC-SHA256）把身份签成 `X-User-Context` 断言，供下游验签后重建 SecurityContext

**为什么在认证之后、转发之前**：
必须在认证完成（userContext 已生成）之后执行，又必须在请求转发到下游之前写入断言头。因此位置在认证后、路由前。

**断言格式**：`v1.<payloadBase64Url>.<signatureBase64Url>`，载荷为紧凑 JSON
（`uid` / `acc` / `roles` / `dept` / `ten` / `iat` / `exp`，时间单位为 epoch 秒）。
签名串为 `v1.<payload>`，因此两侧不需要共享任何 JSON 规范化约定。

**开关**：`carlos.identity-assertion.sign-enabled`（在 Nacos 共享配置 `common.yml` 中，
与全部下游服务共读同一份密钥与开关）。**在请求时读取**而非条件化 Bean，因此改配置/单侧回滚即时生效。

> **已删除**：此处原为 `UserContextRelayFilter`（明文头中继，order `-500`），它把身份降级成
> `X-User-Id` / `X-User-Roles` 等可伪造的明文头，靠下游的 `carlos.resource-server.auth.trusted-ip-ranges`
> （应用层 IP 白名单）证明其不可伪造。该方案有两个结构性问题：挡不住同网段的伪造者；且
> `FeignRequestInterceptor` 会转发所有 `x-` 前缀的头，内部调用时源 IP 变成发起方服务，
> 多主机部署下每次多跳调用都会丢身份。签名断言的完整性与调用方网段无关，已整体替代之。

---

### 阶段八：响应优化

#### 13. ResponseCacheFilter (order = 100)

**作用**：

- 两级缓存：本地 Caffeine L1 + Redis L2
- 仅缓存 GET/HEAD 请求的可缓存响应
- 使用 MurmurHash3 快速生成缓存键

**为什么在转发之前**：
缓存的目的是"避免后端调用"。如果在路由之后执行，请求已经发送到后端服务，缓存就失去了意义。

**技术实现**：`ServerHttpResponseDecorator` 拦截响应体 + MurmurHash3 缓存键。

---

### 阶段九：访问日志

#### 14. AccessLogFilter (order = 1000)

**作用**：

- 记录所有经过 Gateway 的请求信息：method、path、status、duration、requestId、traceId、clientIp
- 使用独立的 `gateway.access` Logger 输出到专用日志文件

**为什么在最后（但 order 不是最大）**：
使用 `doFinally` 模式：虽然 order=1000（在路由前进入过滤链），但实际日志输出发生在 `chain.filter(exchange)`
完成后。由于它在链的较早位置"进入"，它的 `doFinally` 会在整条链（包括 NettyRoutingFilter 的后端调用）完成后执行，因此能捕获最终响应状态码和完整耗时。

**技术实现**：`doFinally` + 独立 Logger + 管道符分隔格式。

## 三、顺序设计原则

### 3.1 分层原则

过滤器按功能分为 9 个阶段，从基础设施到业务逻辑再到日志：

```
可观测性基础 → 准入控制 → 安全防护 → 流量控制 → 认证授权 → 路由准备 → 上下文传递 → 响应优化 → 访问日志
```

### 3.2 依赖优先原则

被依赖的过滤器必须在依赖它的过滤器之前执行：

- `UnifiedWhitelistFilter` → `WafFilter` / `ReplayProtectionFilter` / `OAuth2AuthenticationFilter`
- `OAuth2AuthenticationFilter` → `OAuth2AuthorizationFilter` / `IdentityAssertionSignFilter`
- `PathPrefixFilter` → `RequestTransformFilter`

### 3.3 开销递减原则

越先执行的过滤器开销应该越小（或拦截价值越高）：

1. **Tracing**（极小开销，必须最先）
2. **Metrics**（极小开销，doFinally 模式）
3. **白名单**（内存查询，O(1) 缓存命中）
4. **WAF**（BitSet 预检 + ThreadLocal Matcher）
5. **防重放**（Redis 查 Nonce + HMAC 计算）
6. **限流**（Redis Lua 脚本）
7. **认证**（可能远程验证 Token）
8. **鉴权**（权限缓存 + 匹配）

### 3.4 拦截前置原则

"拒绝类"过滤器（WAF、防重放、限流、认证、鉴权）应尽量前置，越早拒绝，节省的资源越多。

## 四、新增过滤器的指导原则

### 4.1 如何选择 order 值

1. **确定过滤器所属阶段**：根据功能（安全？认证？路由？日志？）确定大致范围
2. **检查依赖关系**：如果被某过滤器依赖，order 应小于它；如果依赖某过滤器，order 应大于它
3. **使用 GlobalFilterOrder 常量**：如果属于现有阶段，直接复用该阶段的常量；如果需要新阶段，在 `GlobalFilterOrder` 中添加新常量
4. **预留间隔**：与相邻过滤器保持至少 100 的间隔，方便后续插入

### 4.2 各阶段可用范围

| 阶段    | 推荐范围          | 备注                   |
|-------|---------------|----------------------|
| 可观测性  | -9500 ~ -8600 | Tracing 和 Metrics 附近 |
| 准入控制  | -8500 ~ -7500 | 白名单附近                |
| 安全防护  | -7500 ~ -5500 | WAF、防重放附近            |
| 流量控制  | -5500 ~ -4800 | 限流附近                 |
| 认证授权  | -4800 ~ -3500 | 认证、鉴权附近              |
| 路由准备  | -3500 ~ -200  | 灰度、路径处理附近            |
| 上下文传递 | -200 ~ 0      | UserContextRelay 附近  |
| 响应优化  | 0 ~ 500       | 缓存附近                 |
| 访问日志  | 500 ~ 2000    | AccessLog 附近         |

### 4.3 禁止事项

- **严禁在过滤器类中硬编码 order 数字**（如 `return -5000`）
- **严禁使用 `Ordered.HIGHEST_PRECEDENCE` 或 `LOWEST_PRECEDENCE` 直接加减**（除 Tracing 外）
- **严禁在 `GlobalFilterOrder` 之外定义新的顺序常量**
- 修改顺序前必须更新本文档

## 五、非 GlobalFilter 组件

以下组件不是 `GlobalFilter`，不通过 `GlobalFilterOrder` 管理顺序：

| 组件                                      | 类型                       | 说明                                |
|-----------------------------------------|--------------------------|-----------------------------------|
| `CarlosRateLimiterGatewayFilterFactory` | GatewayFilterFactory     | 路由级限流，通过路由配置应用                    |
| `Resilience4jCircuitBreakerFilter`      | GatewayFilterFactory     | 路由级熔断，通过路由配置应用                    |
| `SelectStripPrefixGatewayFilterFactory` | GatewayFilterFactory     | 选择性路径前缀剥离，用于 Swagger/Knife4j      |
| `GatewayExceptionHandler`               | ErrorWebExceptionHandler | 全局异常处理，order = HIGHEST_PRECEDENCE |

## 六、常见问题

### Q1: AccessLogFilter 的 order 是 1000，为什么在"最后"？

A: 它使用 `doFinally` 模式。虽然它在过滤链的相对早期位置（order=1000）进入，但它的日志记录逻辑包装在
`chain.filter(exchange).doFinally(...)` 中。`doFinally` 会在整个响应链完成后执行，因此能记录到最终的响应状态码和完整耗时。

### Q2: MetricsFilter 和 AccessLogFilter 有什么区别？

A: 两者都记录请求信息，但用途不同：

- **MetricsFilter**：面向监控，输出 Micrometer 指标到 Prometheus，关注 QPS、延迟、错误率等量化数据
- **AccessLogFilter**：面向审计，输出结构化日志到文件，关注单次请求的完整信息（谁、什么时间、访问了什么、结果如何）

### Q3: 为什么限流在认证之前？

A: 如果限流放在认证之后，攻击者可以无限制地请求认证接口（如暴力破解密码、刷 Token），认证服务会被打垮。限流前置可以保护包括认证服务在内的所有后端服务。

### Q4: PathPrefixFilter 和 RequestTransformFilter 的区别？

A: `PathPrefixFilter` 处理的是"标准前缀剥离"（如 `/api/v1`），这是 Gateway 的通用约定；`RequestTransformFilter` 处理的是"
业务级转换"（如版本控制、路径重写、Header 转换），是更灵活但非标准的操作。先执行标准操作，再执行业务转换，逻辑更清晰。

### Q5: 修改过滤器顺序后如何验证？

A: 启动 Gateway 应用，观察日志中过滤器注册顺序，或使用以下 Actuator 端点：

```bash
# 查看所有已注册的 GlobalFilter
curl http://localhost:8080/actuator/gateway/globalfilters

# 查看路由详情（含 GatewayFilter）
curl http://localhost:8080/actuator/gateway/routes
```
